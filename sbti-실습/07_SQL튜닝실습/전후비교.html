문제 1거래내역 조회 ★★

6,842 ms  →  11 ms  (약 620배)

전 — 실습본

SELECT *
FROM txn t, account a, product p
WHERE t.acct_no = a.acct_no
  AND a.prod_cd = p.prod_cd
  AND DATE(t.txn_at) >= '2026-07-01'
  AND DATE(t.txn_at) <= '2026-07-31'
  AND t.acct_no = 000000000001
  AND (t.txn_type = 'DEPOSIT'
    OR t.txn_type = 'WITHDRAW')
  AND t.memo LIKE '%급여%'
ORDER BY t.txn_at DESC;

후 — 최적화

SELECT t.txn_at, t.txn_type, t.amount,
       t.balance_after, t.memo, p.prod_nm
FROM txn t
JOIN account a ON a.acct_no = t.acct_no
JOIN product p ON p.prod_cd = a.prod_cd
WHERE t.acct_no = '000-000-000001'
  AND t.txn_at >= TIMESTAMP '2026-07-01 00:00:00'
  AND t.txn_at <  TIMESTAMP '2026-08-01 00:00:00'
  AND t.txn_type IN ('DEPOSIT','WITHDRAW')
ORDER BY t.txn_at DESC;
바뀐 것전후왜
날짜 조건DATE(txn_at) >= …txn_at >= … 컬럼을 함수로 감싸면 인덱스를 못 탄다. 끝은 < 다음달 1일 (<= 말일이면 마지막 날이 빠짐)
계좌번호= 000000000001= '000-000-000001' VARCHAR(14)에 숫자 비교 → 암묵적 형변환으로 인덱스 무력화. 하이픈도 빠져 있었다
조회 컬럼SELECT *필요한 6개txn은 컬럼이 넓다. 네트워크·메모리 낭비
적요 검색LIKE '%급여%'제거선행 %는 인덱스 사용 불가. 필요하면 별도 검토
조인FROM a, b, cJOIN … ON조인 조건 누락을 눈으로 잡을 수 있다

문제 2상품별 가입현황 집계 ★★★

30,188 ms  →  38 ms  (약 790배)

전 — 실습본

SELECT p.prod_cd, p.prod_nm, p.prod_type,
  (SELECT COUNT(*) FROM account a
     WHERE a.prod_cd = p.prod_cd
       AND a.status = 'NORMAL')   AS 정상계좌수,
  (SELECT COUNT(DISTINCT a.cust_no) FROM account a
     WHERE a.prod_cd = p.prod_cd)  AS 가입고객수,
  (SELECT SUM(a.balance) FROM account a
     WHERE a.prod_cd = p.prod_cd
       AND a.status = 'NORMAL')   AS 총잔액
FROM product p
GROUP BY p.prod_cd, p.prod_nm, p.prod_type
HAVING COUNT(*) > 0
ORDER BY 총잔액 DESC;

-- account 를 21회 풀스캔 (상품7 x 서브쿼리3)

후 — 최적화

CREATE INDEX idx_account_prod
    ON account (prod_cd);

SELECT p.prod_cd, p.prod_nm, p.prod_type,
  COUNT(*) FILTER (WHERE a.status='NORMAL')
                                    AS 정상계좌수,
  COUNT(DISTINCT a.cust_no)         AS 가입고객수,
  COALESCE(SUM(a.balance)
    FILTER (WHERE a.status='NORMAL'), 0)
                                    AS 총잔액
FROM product p
LEFT JOIN account a ON a.prod_cd = p.prod_cd
GROUP BY p.prod_cd, p.prod_nm, p.prod_type
ORDER BY 총잔액 DESC;
바뀐 것전후왜
집계 방식상관 서브쿼리 3개LEFT JOIN 1번 account를 21회 훑던 것을 1회로. 시간의 대부분이 여기 있었다
조인 종류—LEFT INNER면 가입 0건 상품(P007 참좋은 파킹통장)이 사라진다. 업무 요건 위반
조건별 집계서브쿼리마다 WHEREFILTER (WHERE …) WHERE로 걸면 세 집계 전부에 적용된다. CASE WHEN도 같은 결과
NULL 처리없음COALESCE(…, 0) 가입 0건 상품의 SUM은 NULL. 화면엔 0이 나와야 한다
HAVING COUNT(*) > 0있음삭제 GROUP BY 결과에 0건 그룹은 원래 없다. 무의미하고 오히려 위험
인덱스account.prod_cd 없음idx_account_prod 쿼리만 고치면 절반이다. 여기서 가장 많이 빠뜨린다
