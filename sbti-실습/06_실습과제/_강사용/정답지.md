**6. 예약 겹침 버그 ★★★**

`backend/services/booking-service.js` **17번째 줄**, `hasConflict()` 안

```js
if (newStart >= r.end_at || newEnd < r.start_at) continue;   // ← 버그
```

뒤쪽이 `<` 라서, **새 예약의 끝 시각과 기존 예약의 시작 시각이 정확히 같을 때**
(= 딱 붙여서 예약할 때) 겹친다고 잘못 판단해 예약이 거부됩니다.

```js
if (newStart >= r.end_at || newEnd <= r.start_at) continue;   // 올바른 코드
```

앞쪽(`>=`)은 올바르므로 **한쪽만 틀린 비대칭 버그**입니다. 그래서 눈에 잘 안 띕니다.

- 모델이 자주 틀리는 지점: 이 문제는 35B 모델이 **혼자서는 거의 못 찾습니다.**
  힌트 2("끝시각 == 시작시각일 때 어떻게 판정되나")까지 주면 대부분 맞힙니다.
  못 찾더라도 정상입니다 — 오히려 **"AI가 놓치는 종류의 버그가 있다"**는 걸
  체험시키는 것이 이 문제의 목적입니다.

# SQL 튜닝 정답

## 실습 A — `database/tuning/slow-reservation-query.sql` ★★

### 첫 번째 쿼리의 문제 4가지

| # | 문제 | 왜 |
|---|---|---|
| 1 | `DATE(r.start_at) = '2026-08-10'` | 인덱스 컬럼을 함수로 감싸면 인덱스를 못 탄다(sargable 아님) |
| 2 | `r.emp_no = 1234567` | `emp_no` 는 `VARCHAR(7)` 인데 숫자로 비교 → 암묵적 형변환으로 `idx_reservations_emp` 무력화 |
| 3 | `SELECT *` | 필요한 컬럼은 7개인데 전체를 읽는다. 커버링 인덱스 기회도 날린다 |
| 4 | `purpose LIKE '%회의%'` | 앞에 `%` 가 붙으면 인덱스 사용 불가. 게다가 `purpose` 엔 인덱스 자체가 없다 |

부가: `status` 의 `OR` 는 `IN` 으로 쓰는 편이 낫다(옵티마이저가 처리하긴 한다).

### 고친 쿼리

```sql
SELECT r.id, r.room_id, m.name, r.start_at, r.end_at, r.purpose, r.status
FROM reservations r
JOIN rooms m ON m.code = r.room_id
WHERE r.start_at >= TIMESTAMP '2026-08-10 00:00:00'
  AND r.start_at <  TIMESTAMP '2026-08-11 00:00:00'   -- 다음날 00:00 미만 (<= 아님)
  AND r.emp_no = '1234567'                            -- 따옴표
  AND r.status IN ('CONFIRMED', 'PENDING')
ORDER BY r.start_at DESC;
```

`LIKE '%회의%'` 는 **조건 자체를 뺐다.** 꼭 필요하면 애플리케이션에서 거르거나
전문검색 인덱스를 따로 만들어야 한다. 이걸 "그냥 두면 된다"고 답하면 오답.

### 두 번째 쿼리

- `DATE(start_at) BETWEEN ...` → 같은 함수 문제. 범위 비교로 바꾼다
- `UPPER(r.status) = 'CONFIRMED'` → 이미 대문자로 저장되므로 `UPPER` 불필요
- `FROM reservations r, rooms m` 콤마 조인 → `JOIN ... ON` 명시적 조인
  (조인 조건을 빠뜨리면 카티션 곱이 되는데 콤마 조인은 그걸 눈치채기 어렵다)

### 모델이 자주 틀리는 지점

- **경계값**: `< '2026-08-11'` 을 `<= '2026-08-10 23:59:59'` 로 쓰는 경우가 많다.
  TIMESTAMP 는 초 미만 값이 있을 수 있어 `< 다음날 00:00` 이 안전하다. 이걸 짚어주면 좋다.
- `emp_no` 따옴표를 빼먹는다. 타입을 명시적으로 알려줘야 고친다.
- `LIKE` 조건을 **그대로 남겨두고** 나머지만 고치는 경우가 흔하다.

## 실습 B — `database/tuning/slow-usage-report.sql` ★★★

### B-1 : 상관 서브쿼리 3개 → JOIN 1개

문제: 회의실 1건마다 `reservations` 를 3번 훑는다. 7개 회의실 × 3 = **21회 풀스캔.**

```sql
SELECT m.code,
       m.name,
       COUNT(*) FILTER (WHERE r.status = 'CONFIRMED')                    AS total_cnt,
       COUNT(DISTINCT r.emp_no)                                          AS user_cnt,
       COALESCE(SUM(EXTRACT(EPOCH FROM (r.end_at - r.start_at)) / 60)
                FILTER (WHERE r.status = 'CONFIRMED'), 0)                AS used_minutes
FROM rooms m
LEFT JOIN reservations r ON r.room_id = m.code
WHERE m.active = true
GROUP BY m.code, m.name
ORDER BY used_minutes DESC;
```

핵심 3가지

1. **`LEFT JOIN`** 이어야 한다. `INNER JOIN` 이면 예약 0건인 회의실이 사라진다
2. `status` 조건이 붙은 집계와 안 붙은 집계가 섞여 있으므로
   `FILTER (WHERE ...)` (또는 `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`) 로 구분
3. `SUM` 결과가 `NULL` 이 될 수 있어 `COALESCE(..., 0)`

`idx_reservations_room_time (room_id, start_at, end_at)` 의 선두 컬럼이 `room_id` 라
조인 자체는 인덱스를 탄다. 문제는 인덱스가 아니라 **21번 반복**이었다.

### B-2 : 인덱스 누락 + 불필요한 구문

```sql
SELECT a.actor, u.name, u.dept, COUNT(*) AS action_cnt
FROM audit_log a
JOIN users u ON u.emp_no = a.actor
WHERE a.created_at >= NOW() - INTERVAL '30 days'
GROUP BY a.actor, u.name, u.dept
ORDER BY action_cnt DESC;
```

- **`HAVING COUNT(*) > 0` 삭제** — `GROUP BY` 결과에 0건 그룹은 애초에 없다. 무의미하다
- 콤마 조인 → 명시적 `JOIN`
- **인덱스 추가가 진짜 답이다.** `audit_log` 에는 PK 말고 인덱스가 없다

```sql
CREATE INDEX idx_audit_log_created ON audit_log (created_at);
CREATE INDEX idx_audit_log_actor   ON audit_log (actor);
-- 또는 한 번에
CREATE INDEX idx_audit_log_created_actor ON audit_log (created_at, actor);
```

탐색 문제 8번(인덱스 없는 테이블 = `audit_log`)과 이어지는 문제다.
8번을 먼저 풀게 하면 여기서 "아, 그 테이블" 하고 연결된다.

### 모델이 자주 틀리는 지점

- **`INNER JOIN` 으로 바꿔버린다.** 예약 0건 회의실이 사라지는 걸 스스로 못 잡는다.
  "예약이 없는 회의실도 결과에 나와야 한다"고 조건을 줘야 `LEFT JOIN` 을 쓴다.
- `FILTER` 문법을 모르면 `CASE WHEN` 으로 쓴다 — **둘 다 정답**이다
- `COALESCE` 를 빼먹어 `used_minutes` 가 `NULL` 로 나온다
- B-2에서 쿼리만 고치고 **인덱스 생성을 안 적는다.** 이게 핵심인데 놓친다
