# SBTI 1·2·3 강의 운영 준비 가이드

조사 기준일: 2026-07-29
운영 조건: 각 120분 × 3회 × 회차당 40명, 총 120명

## 1. 결론부터

현재 `sbti1`, `sbti2`, `sbti3`은 각각 15장, 31장, 13장으로 총 59장이다. 발표자료로는 충분하지만, 그대로 2시간 실습수업을 운영하기에는 다음 항목이 비어 있다.

- 참가자 설치·계정·권한 확인 절차
- 수업별 학습목표와 완료 기준
- 참가자용 실습 저장소와 실습지
- 40명 질문·장애 대응 방식
- 네트워크·SSO·API Key·모델 장애 시 대체 시나리오
- 수업 중 안전수칙과 회사 데이터 사용 기준
- 제품·성과 수치의 근거 분류
- 수업 성과를 확인할 간단한 평가

따라서 지금 해야 할 일은 슬라이드를 늘리는 것이 아니라, 아래 다섯 가지를 붙여 “운영 가능한 과정”으로 만드는 것이다.

1. 수업별 하나의 핵심 실습
2. 사전 설치·접속 점검
3. 강사 1명 외 보조 진행 인력
4. 네트워크가 없어도 가능한 대체 실습
5. 근거가 있는 표현과 5분 안전 브리핑

## 2. 인력과 좌석 운영

40명이 동시에 코딩 에이전트를 사용하면 강사가 설명과 개별 장애 대응을 같이 맡을 수 없다. The Carpentries는 일반적인 워크숍 팀을 host, 2명 이상의 instructor, helpers로 구분하고, 한 명이 설명할 때 다른 사람이 교실을 돌며 돕는 “teach and assist” 방식을 안내한다. 고정된 보조자 비율을 제시하지는 않는다. [The Carpentries: Working With Your Team](https://carpentries.github.io/instructor-training/21-management.html)

이 과정에서는 다음 구성을 운영 목표로 둔다. 이는 보편 법칙이 아니라 40명·사내 계정·AI 도구 실습이라는 조건에 맞춘 운영 판단이다.

- 강사 1명: 설명, 라이브 데모, 전체 속도 결정
- 공동 진행 또는 수석 helper 1명: 공통 장애 판단, 강사에게 중단 신호
- helper 2명: 설치·계정·권한·실습 오류 순회 지원
- 별도 host 1명: 출석, 좌석, 마이크, 시설, 공지 담당

총 5명은 이 과정의 최소 운영 목표다. 사전 설치 완료율이 낮거나 참가자 기기·숙련도·접근성 요구가 다양하면 helper를 더 확보해 6~8명 체제로 운영하는 편이 안전하다. 실제 필요 인원은 T-7 리허설의 도움 요청 건수와 대기시간으로 확정한다.

학습자는 4명씩 10개 조로 앉힌다. helper 3명이 각각 3~4개 조를 맡고, 조 안에서는 다음 역할을 15분마다 교대한다.

- Driver: 직접 키보드를 조작
- Navigator: 요구사항과 다음 단계 확인
- Reviewer: diff·테스트·위험 확인
- Recorder: 오류와 해결방법 기록

도움 요청은 손들기 대신 파란색/노란색 카드나 온라인 대기열을 쓴다.

- 파란색: 완료, 다음 단계 가능
- 노란색: 도움이 필요하지만 계속 작업 중
- 노란색 요청이 8개 이상 쌓이면 강사가 전체 진행을 멈추고 공통 원인을 설명

색각 다양성을 위해 빨강·초록 조합은 피한다. 이 방식은 도움 요청을 눈에 보이게 하고 학습자가 기다리는 동안 계속 작업할 수 있게 한다. [The Carpentries: Working With Your Team](https://carpentries.github.io/instructor-training/21-management.html)

## 3. 세 수업의 학습목표

### SBTI 1: AI 코딩 도구 지형과 안전한 첫 루프

수업이 끝나면 참가자는 다음을 할 수 있어야 한다.

- Web UI, 데스크톱, IDE, CLI 코딩 에이전트의 차이를 설명한다.
- 에이전트의 `요청 → 탐색 → 수정 → 실행 → 검증` 루프를 설명한다.
- 작은 변경을 위임하고 diff와 테스트로 결과를 검증한다.
- 제품명이나 인기보다 업무·권한·검증 방식으로 도구를 선택한다.

### SBTI 2: 택가이코드로 저장소 이해·지식화·검증

수업이 끝나면 참가자는 다음을 할 수 있어야 한다.

- 택가이Web과 택가이코드의 역할을 구분한다.
- Terminal과 VS Code에서 같은 에이전트 루프가 어떻게 동작하는지 설명한다.
- 코드를 바꾸기 전에 저장소 구조와 진입점을 읽기 전용으로 찾는다.
- 제공된 가이드 문서를 지식으로 참조하고, 근거와 추론을 구분한다.
- 권한 거절·테스트 실패·잘못된 답변을 복구한다.

### SBTI 3: 실제 사례와 사내 프레임워크 연계

수업이 끝나면 참가자는 다음을 할 수 있어야 한다.

- React POC에서 요구사항 파악, 구조 분석, 수정, 검증 흐름을 설명한다.
- 문서 지식화와 MCP의 역할·차이·신뢰 경계를 설명한다.
- ProFrame·WebSquare·Java 연계를 재현 가능한 부분과 개념 시연 부분으로 구분한다.
- 작은 React 변경을 수행하고 결과를 테스트·설명한다.
- MCP 서버 추가가 곧 신뢰를 의미하지 않는다는 점을 설명한다.

## 5. 핵심 실습과 대체 실습

### SBTI 1 실습: 로그인 화면 한 번의 안전한 변경

제공물:

- 작은 웹 프로젝트
- 명확한 변경요청 1개
- 실행 명령 1개
- 테스트 또는 체크 명령 1개
- 일부러 넣은 잘못된 AI 제안 1개

완료 기준:

- 참가자가 변경 전 요구사항을 한 문장으로 쓴다.
- 에이전트가 수정한 diff를 찾는다.
- 테스트·빌드·브라우저 중 하나로 동작을 확인한다.
- 받아들인 변경과 거절한 변경을 각각 설명한다.

### SBTI 2 실습 1: 이해한 뒤 바꾸기

1. 저장소 구조와 진입점을 찾는다.
2. 기능과 관련된 파일을 근거와 함께 제시한다.
3. 변경 계획만 만들고 바로 수정하지 않는다.
4. 읽기 전용 검사나 테스트를 실행한다.

완료 기준: 정확한 진입점, 근거 파일, 무단 수정 없음, 불확실성 표시.

### SBTI 2 실습 2: 문서에 근거한 답변

1. 제공된 가이드 PDF 또는 Markdown을 지식으로 등록한다.
2. 규칙·관련 파일·승인 절차를 질문한다.
3. 답변에서 문서 근거와 모델 추론을 구분한다.
4. 문서에 없는 규칙은 “확인 필요”로 표시한다.

### SBTI 3 실습: React 작은 흐름 수정

땡겨요 전체 POC를 재현하지 않는다. 회원가입·검색·주문 중 하나의 작은 검증, 메시지, 상태 처리만 바꾼다.

완료 기준:

- 요구사항과 기존 동작을 먼저 적음
- 관련 컴포넌트·상태·테스트를 찾음
- 작은 diff
- 실행 또는 테스트 증거
- 변경을 60초 안에 설명

### 공통 오프라인 대체 실습

네트워크·SSO·API Key·모델 장애 시 다음 묶음으로 동일한 학습목표를 유지한다.

- 사전 캡처한 에이전트 대화
- 변경 전/후 diff
- 테스트 성공·실패 로그
- 안전한 제안 2개와 위험한 제안 1개
- 참가자 과제: 위험한 제안을 찾고, 필요한 검증과 수정 프롬프트 작성

## 8. 성과수치와 제품주장 관리

각 수치는 다음 다섯 등급 중 하나를 슬라이드 노트에 표시한다.

1. 감사·결재 확정
2. 운영 로그 집계
3. 내부 POC 측정
4. 사용자 후기
5. 추정·가설·로드맵

수치별 근거표에 반드시 적을 항목:

- 슬라이드 번호와 정확한 문장
- 데이터 기준일
- 책임 부서·담당자
- 원본 문서·쿼리·대시보드
- 모집단·표본·분모
- 비교 기준과 계산식
- 제외한 비용 또는 조건
- 일반화 가능 범위
- 외부/사내 교육에서 말해도 되는지
- 발표할 때 사용할 한 문장

예시:

- “87.5%”: 단일 POC의 최대값인지, 화면당 평균인지, 기준 MM과 대상 화면 수가 무엇인지 확인
- “17억~90억”: AI 생성 추정이라면 감사 확정 절감과 같은 문단에서 섞지 않음
- “1,743명·619 WAU”: 운영 로그 기준일과 중복 사용자·활성 정의 명시
- “50+ tools”와 “37 tools”: 제품 버전별 실제 inventory를 수업 전 다시 계산
- “검증 완료·기본 탑재·실사용”: 검증 주체, 배포 버전, 실제 사용 부서 확인

## 9. 수업 중 측정할 것

수업 성과는 코드 줄 수나 프롬프트 개수로 보지 않는다. 연구에서는 AI가 특정 업무 출력량을 높인 사례와 고맥락 숙련 작업을 느리게 한 사례가 모두 있고, 즉시 결과가 좋아도 독립 이해·디버깅이 낮아질 수 있다. [METR 2025](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/), [Microsoft Research 2025](https://www.microsoft.com/en-us/research/publication/the-effects-of-generative-ai-on-high-skilled-work-evidence-from-three-field-experiments-with-software-developers/), [Anthropic 2026 skill study](https://www.anthropic.com/research/AI-assistance-coding-skills)

회차마다 기록할 항목:

- 로그인 성공까지 걸린 시간
- 첫 프롬프트, 첫 diff, 첫 테스트까지 걸린 시간
- helper 없이 실습을 완료한 조 수
- 모델/도구 장애와 참가자 오류를 분리한 개수
- AI 제안을 수락·거절한 이유
- 테스트 또는 실행 증거 보유 여부
- 참가자가 AI 없이 변경 내용을 설명할 수 있는지
- 종료 시 미해결 질문 수

출구 질문:

1. 다음 출근일에 바로 적용할 한 가지
2. 절대 넣지 않을 데이터나 비밀 한 가지
3. AI 결과를 확인할 검증 한 가지
4. 아직 막힌 한 가지
