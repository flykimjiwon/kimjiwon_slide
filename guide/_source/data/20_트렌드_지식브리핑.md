# A. 구조 지식

## 1. 큰 그림 — 2026년 7월, 우리가 서 있는 좌표

### 1-1. AI 엔지니어링 성숙도 3단계 🟢

업계가 공유하는 프레임이 하나 있고, 이게 당신 sbti2의 "하네스 엔지니어링" 슬라이드의 이론적 뿌리다.

```
2022–2023   프롬프트 엔지니어링   "무엇을 시킬지"      — 문장을 다듬는다
2024–2025   컨텍스트 엔지니어링   "무엇을 보여줄지"    — 창에 넣을 것을 고른다
2026–        하네스 엔지니어링    "어떻게 일하게 할지"  — 행동·검증·재시도를 설계한다
```

핵심 공식: **Agent = Model + Harness**

- 모델은 사서 쓴다(또는 오픈웨이트로 받는다). **차별화는 하네스에서 난다.**
- 이 공식이 당신 제품(택가이코드)의 존재 이유를 한 줄로 설명한다. → *"내부망 모델이 프론티어가 아니어도, 하네스로 따라잡는다."* 이게 sbti2 슬라이드 307~310행에 이미 적혀 있는 말이고, 이제 업계 표준 용어로 뒷받침된다.

### 1-2. "하네스가 모델보다 중요하다"의 실증 근거 (강의에서 반드시 쓸 카드)

| 근거 | 내용 | 신뢰도 |
|---|---|---|
| **LangChain / Terminal-Bench 2.0** | 모델을 **전혀 바꾸지 않고** 하네스만 최적화해서 30위 → 5위 | 🟡 |
| **OpenAI 하네스 엔지니어링 (2026-02, Ryan Lopopolo)** | 엔지니어 3명이 Codex로 **약 100만 줄 / PR 약 1,500건**을 손으로 코드 한 줄 안 쓰고 완성. 수작업 대비 **약 1/10 시간**. 단일 실행이 **6시간 연속** 작동 | 🟢 (OpenAI 공식 포스트) |
| **SWE-bench 점수 편차** | 같은 모델이 하네스에 따라 **10점 이상** 흔들린다. 벤더 자체 스캐폴딩 점수와 통제된 harness 점수가 다름 | 🟡 |
| **"Is Grep All You Need?" (arXiv 2605.15184)** | 검색 방식(grep vs 벡터)을 바꾼 효과와 **하네스를 바꾼 효과가 비슷한 크기**였다. 결론: *"retrieval is really retrieval-plus-orchestration"* | 🟢 (논문) |

명언 두 개 (슬라이드에 인용 가능):
- **"Agents aren't hard; the Harness is hard."** — Ryan Lopopolo, OpenAI
- **"Humans steer. Agents execute."** — 같은 글

### 1-3. 그래서 2026년의 한 문장

> 2025년은 "에이전트가 코드를 쓸 수 있는가"를 증명한 해였고,
> 2026년은 **"에이전트를 궤도에서 이탈하지 않게 붙잡아 두는 시스템을 누가 잘 만드는가"** 의 해다.

## 2. 모델 지형 — 이름 말고 축으로 가르쳐라

### 2-1. 강의에서 쓸 4개 축 (이것만 가르치면 이름이 바뀌어도 안 무너진다)

1. **가중치 공개 여부** — 폐쇄형(API만) vs 오픈웨이트(다운로드 가능) → **온프렘 가능 여부를 결정**. 택가이코드의 존재 근거.
2. **추론(thinking) 유무** — 일반 모델 vs 추론 모델. 추론 모델은 답하기 전 "생각 토큰"을 태워 수학·코드·계획에 강하지만 느리고 비싸다.
3. **컨텍스트 창 vs 실효 컨텍스트** — 광고 창(1M)과 실제로 정확한 구간(대개 200~400K)은 다르다.
4. **가격 구간** — 입력/출력 비대칭(출력이 2~6배), 프롬프트 캐시(최대 90% 할인), 배치(50% 할인).

### 2-2. 2026년 7월 현재 지형 (개략 — 🟡, 이름은 흔들림)

**폐쇄형 프론티어 3사**
- **Anthropic Claude 5 계열** — Fable 5 / Opus 5 / Sonnet 5, 소형은 Haiku 4.5. Sonnet 5는 2026-06-30, Opus 5는 2026-07-24 발표. Opus 5의 지식 컷오프는 2026년 5월. 🟢(Anthropic 공식 뉴스)
- **OpenAI GPT-5 계열** — 5.3-Codex(코딩 특화), 5.5, 5.6(Luna/Terra/Sol) 등 세부 버전이 빠르게 갈라짐. 🟡
- **Google Gemini 3 계열** — 3.5 Flash / 3.6 Flash / Flash-Lite 계열이 2026년 7월에 릴리스, 3.5 Pro는 지연·소문 다수. **Gemini는 롱컨텍스트에서 우위**라는 평가가 반복 등장. 🟡

**오픈웨이트 / "대륙 시리즈"** (sbti1의 "대륙 코드 어시스턴트 시리즈" 슬라이드 근거)
- DeepSeek, Qwen(Alibaba), Kimi(Moonshot), GLM(Z.ai/Zhipu), MiniMax — 5개 랩이 프론티어급 오픈웨이트를 낸다.
- 대체로 알려진 성격: **DeepSeek=효율·추론, Qwen=사이즈 다양·라이선스 관대(Apache 2.0 다수)·자체호스팅, Kimi=에이전틱 롱호라이즌, GLM=프론트엔드/가성비, MiniMax=저비용 대량처리**. 🟡
- **강의 포인트**: 이들이 "코드 어시스턴트 CLI"까지 직접 낸다는 게 sbti1의 "Webui → CLI → IDE" 흐름 주장의 실제 근거다. 그리고 **이 계열이 곧 온프렘 후보군**이라 sbti2로 자연스럽게 연결된다.
- 하드웨어 현실: 최상위 MoE는 80GB급 멀티 GPU 또는 512GB 통합메모리급이 필요. 🟡 → 내부망 인프라 이야기로 연결.

**⚠️ 벤치마크 수치는 인용하지 마라.** 이번 조사에서 SWE-bench Verified 상위값이 출처별로 76.8% ~ 96.2%까지 벌어졌다. 하네스·스캐폴딩·검증주체가 다 다르다. 대신 이렇게 말하라:

> "리더보드 숫자는 모델만의 점수가 아니라 **모델 + 하네스 + 채점방식의 합산**입니다. 그래서 같은 모델이 어디서 재느냐에 따라 10점 넘게 흔들립니다. 우리가 봐야 할 건 순위가 아니라 **우리 코드베이스에서의 재현 가능한 성공률**입니다."

이 한 마디가 강의 전체에서 가장 '고수처럼' 들리는 문장이다.

### 3-2. 2026년 코드 어시스턴트에서 실제로 일어난 일 (🟡)

- **Copilot**: 설치 기반 최대(2026년 1월 유료 460~470만 구독 규모). 대기업 침투율 높음. 다만 "주력 도구" 선호도는 다른 데로 감.
- **Cursor**: 매출 선두(2026년 초 ARR 2B 규모 보도), 자체 모델(Composer) 보유, 2026년 들어 **Composer 사이드패널 → Agents Window로 UI 자체를 멀티에이전트 중심으로 재편**. 클라우드 에이전트 추가.
- **Claude Code**: 개발자 만족도/주력도구 점유율 선두 보도. 2026년에 **Agent Teams(한 세션이 팀장이 되어 팀원 에이전트 생성·자율조율), agent view(백그라운드 세션 대시보드), 원격 이어받기(PC→폰)** 등이 추가.

- **Google Antigravity**: 2025-11 Gemini 3와 함께 등장한 agent-first IDE(VS Code 포크) → 2026 I/O에서 **2.0으로 데스크톱 앱 + CLI + SDK 플랫폼화**. Antigravity CLI(Go)가 Gemini CLI를 대체하며 **Agent Skills / Hooks / Subagents / plugins**를 계승.
- **GitHub Agent HQ**: 여러 벤더 에이전트(Copilot·Claude·Codex 등)를 **한 곳(mission control)에서 배정·감시·중단**하는 엔터프라이즈 관제. 2026-02 퍼블릭 프리뷰.

> **당신 슬라이드와의 연결**: sbti1의 "실제로는 이렇게 쓴다 — cmux 멀티탭"과 "ADE, 그리고 Orca"가 바로 이 흐름이다. 업계 전체가 **"한 창에서 한 에이전트" → "여러 에이전트를 관제"** 로 UI를 갈아엎는 중이라는 게 2026년의 큰 그림이고, 당신 sbti2의 "멀티세션 / 멀티에이전트" 두 장이 정확히 그 지점에 있다.

### 3-3. ⚠️ sbti1의 "ChatGPT 앱 — Codex에서 개명" 슬라이드

**정확하지 않다.** 실제로는 기존 **Codex 데스크톱 앱이 새 ChatGPT 데스크톱 앱으로 흡수**되었고, 그 안에서 **Codex는 별도 뷰로 남는다**. "Codex가 ChatGPT로 개명"이 아니다. 방향이 반대에 가깝다.

## 4. 에이전트 루프 — 원리 (sbti1 1번 슬라이드 심화)

### 4-1. 루프의 정체

```
목표 수신 → 계획 → 도구 선택 → 도구 실행 → 결과를 컨텍스트에 삽입 → 판단 → (반복) → 중단/보고
```

핵심은 **LLM은 아무것도 하지 않는다**는 것. LLM은 "이 도구를 이 인자로 부르겠다"는 **구조화된 출력**을 뱉을 뿐이고, 실제 실행은 하네스가 한다. sbti2의 285~310행("AI가 도구를 쓰는 순서")이 정확히 이걸 그리고 있다. 여기에 한 문장만 더 붙이면 완성된다:

> **"모델은 '무엇을 하고 싶다'고 말할 뿐이고, 실제로 할지 말지는 하네스가 결정합니다. 그래서 보안은 모델이 아니라 하네스에 겁니다."**

### 4-2. Workflow vs Agent (반드시 구분해서 가르칠 것)

| | Workflow | Agent |
|---|---|---|
| 단계 | 사람이 미리 고정 | 모델이 동적으로 결정 |
| 예측가능성 | 높음 | 낮음 |
| 감사·규제 적합 | 좋음 | 어려움 |
| 적합 과업 | 정형·반복·규정준수 | 탐색·분해·미지의 코드베이스 |

**금융권 강의에서 특히 중요**: "전부 에이전트로 하자"가 아니라 **"규정이 걸린 곳은 워크플로, 탐색이 필요한 곳은 에이전트"** 가 정답이라고 못박아라. 이 한 마디로 컴플라이언스 쪽 청중의 신뢰를 얻는다.

### 4-3. 검색 방식의 대전환 — 벡터 RAG → 에이전틱 검색 🟢

**이건 강의에서 반드시 다뤄라. 대부분의 청중이 "AI 코딩 = RAG/벡터DB"라고 잘못 알고 있다.**

- 2025년 5월, **Claude Code는 벡터 검색을 걷어내고 grep으로 갈아탔다.** 임베딩 파이프라인·로컬 벡터DB·청킹 휴리스틱을 전부 제거. 결과는 "압도적으로 더 좋았다".
- 이후 Cursor, Windsurf, Cline, Devin, Amp 등이 유사한 방향으로 이동. 🟡
- 이유: 코드는 **정확한 식별자**로 찾는 게 맞다. 인덱스 동기화 문제도 없고, 항상 **현재 파일 상태**를 본다.
- 논문 근거: "Is Grep All You Need?"(arXiv 2605.15184) — inline 전달 방식에서는 **모든 하네스-모델 조합에서 lexical(grep)이 dense retrieval보다 일관되게 강했다**. 단, 노이즈가 커지면 교차점이 생기고 그 교차점은 하네스마다 다르다.
- Amazon Science(AAAI 2026): 에이전틱 키워드 검색이 **벡터 스토어 없이 RAG faithfulness의 94.5%** 도달. 🟡

> **당신 제품과의 연결**: 택가이코드의 `grep_search` / `glob_search` / `file_read` / `knowledge_search` 조합(sbti3의 37 tools 슬라이드)이 바로 이 최신 설계다. "우리는 유행 지난 RAG를 안 쓴다"가 아니라 **"업계가 2025년에 벡터를 버리고 온 방향에 우리가 이미 서 있다"** 로 말하면 훨씬 강하다.
> 단, **지식화(문서 파싱→.md→검색)는 여전히 유효**하다. 코드는 grep, **문서·가이드는 검색형 지식**이 맞다. 이 구분을 명확히 하라.

## 5. 하네스 엔지니어링 — sbti2의 킬러 슬라이드 심화

### 5-1. 정의 🟢

> **하네스**: LLM을 둘러싸고, 모델의 추론을 제외한 **모든 것**을 담당하는 소프트웨어. 도구 실행, 상태 관리, 메모리, 권한, 검증, 재시도, 관측.
> **하네스 엔지니어링**: 에이전트가 올바른 절차로 끝까지 일하도록 **작업환경·제약조건·피드백 루프**를 설계하는 규율.

Mitchell Hashimoto의 실천 원칙(2026-02, 🟡 원문 URL 미확인):
> *"에이전트가 실수하면, 그 실수를 다시는 못 하게 환경에 영구적인 해결책을 심는다."*

### 5-2. 하네스 5대 구성요소 (강의용 표준 분해)

| # | 구성요소 | 하는 일 | 택가이코드 대응 |
|---|---|---|---|
| 1 | **도구 오케스트레이션** | 도구 선택·연쇄·에러 처리 | 37~50+ built-in tools, MCP |
| 2 | **검증 루프** | 테스트·린트·진단 결과를 다시 모델에 주입 | `run_test`, `diagnostics`, `code_review_local` |
| 3 | **컨텍스트 & 메모리** | 규칙·지식·세션 상태 | `rules.md`, `.techai.md`, 지식화 |
| 4 | **가드레일** | 샌드박스, 예산 상한, 승인 게이트 | allow/ask/deny, `permissions.yaml` |
| 5 | **관측성** | 트레이스·감사로그 | 택가이Web의 사용량·오류·메시지 로깅 |

**sbti2 슬라이드(377~389행)는 3개(지시·맥락 / 도구·제약 / 검증·피드백)로 되어 있다. 여기에 5번 관측성을 붙이면 "금융권 하네스"로 완성된다.** 금융권 청중에게는 감사추적이 곧 도입 가능성이므로, 이 한 칸이 슬라이드의 설득력을 가장 크게 올린다.

### 5-3. OpenAI의 실제 하네스 실무 (강의에서 그대로 인용 가능) 🟢

OpenAI가 코드 한 줄 손으로 안 쓰고 100만 줄을 만든 방법:

1. **점진적 공개(progressive disclosure)** — `AGENTS.md`를 **약 100줄의 목차**로만 유지하고, 상세 지침은 `docs/` 하위(design-docs, exec-plans, product-specs, references)로 분리. 원칙: *"컨텍스트는 희소 자원이다."*
2. **기계적 강제** — 계층 의존 규칙(`Types → Config → Repo → Service → Runtime → UI`)을 **린터로 차단**. 에러 메시지에 **수정 방법까지 적어서** 그게 곧 에이전트의 컨텍스트가 되게 함.
3. **저장소가 단일 진실 원천** — 설계문서·실행계획·기술부채 트래커를 전부 버전관리되는 마크다운으로.
4. **피드백 루프** — worktree별 격리 인스턴스 기동, DOM 스냅샷·스크린샷 캡처, 로그/메트릭 질의 → 고침→재시작→재검증 반복.
5. **기술부채 가비지 컬렉션** — 백그라운드 작업이 패턴 위반을 스캔해 **리팩터링 PR을 자동 생성**.

> 이 5개를 슬라이드 한 장으로 만들면 **당신 강의에서 가장 실무적인 장면**이 된다. 청중이 "우리 팀에서 당장 뭘 해야 하나"에 대한 답을 여기서 얻는다. `AGENTS.md 100줄 목차` 하나만으로도 강의가 기억된다.

### 5-4. 오픈소스 하네스 생태계 (sbti1의 "하네스 계열" 슬라이드 보강)

- **Superpowers** (Jesse Vincent) — Claude Code 플러그인. 2025-10-09 출시, 2026-01-15 Anthropic 공식 마켓플레이스 등재. **clarify → design → plan → code → verify 5단계 규율**을 강제해서 "일단 코딩부터" 실패모드를 제거. 🟡
- **oh-my-claudecode(OMC), 가재코드(GJC), LazyCodex, Ouroboros** — 커뮤니티 하네스 번들.
- **Agent Skills / plugins 마켓** — 2026년 들어 수천 개 규모로 폭증. 🟡
- **공통 패턴**: 이들이 전부 하는 일은 같다 — ① 역할 분리 ② 단계 강제 ③ 검증 게이트 ④ 재사용 절차. **당신 슬라이드에서 "이것 외에도 많음.."이라고 넘어가는 대신, 이 4개 공통 패턴을 말해주면 청중이 "아 그래서 저게 다 비슷하구나"를 얻는다.**

### 5-5. 강의용 하네스 비유 (120명 중 비개발자·관리자용)

> "모델은 운전 실력이고, 하네스는 **차선, 가드레일, 속도계, 블랙박스, 그리고 브레이크**입니다.
> 운전 실력이 최고여도 밤에 차선 없는 산길에서는 사고가 납니다.
> 우리 내부망 모델은 F1 드라이버는 아니지만, **우리가 도로를 직접 깔았습니다.**"

## 6. 컨텍스트 엔지니어링 — "많이 넣으면 좋다"는 틀렸다

### 6-1. Context Rot (컨텍스트 부패) 🟢

- 정의: 관련 없는 도구 출력·낡은 중간상태·중복 재읽기가 쌓이면서 **모델이 조용히 정확도를 잃는 현상**.
- 무서운 점: **에러가 안 난다.** 그냥 신호에 덜 집중한다.
- Chroma 연구(18개 프론티어 모델): **200K 창이 5만 토큰에서 이미 심각한 정확도 손실**을 보일 수 있다. 1M 창이 1M을 신뢰성 있게 추론하지 못한다.
- 실무 결론: **광고 컨텍스트(1M)가 아니라 실효 컨텍스트(대략 200~400K)로 설계하라.** 🟡
- 특히: needle과 주변 텍스트가 **의미적으로 비슷할수록** 정확도가 급락한다. 길이보다 **유사 방해자(distractor)** 가 더 치명적이다.

### 6-2. Compaction (압축) 🟢

- 정의: 창이 차기 전에 대화를 요약해 새 창으로 이어붙이는 것.
- Anthropic API에 `compact_20260112`(2026-04 기준 베타)가 있고, 임계값(최소 50K, 기본 150K), 커스텀 요약 프롬프트, 압축 후 일시정지 옵션 등을 제공. 🟡
- 실무: **압축은 무손실이 아니다.** 압축 직후 에이전트가 "아까 정한 규칙"을 잊는 일이 흔하다. → **중요한 결정은 대화가 아니라 파일(저장소)에 적어라.** 이게 OpenAI가 "repo가 단일 진실 원천"이라고 한 이유.

### 6-3. 좋은 컨텍스트의 구성 (강의 체크리스트)

```
□ 목표와 완료 기준       ← 없으면 에이전트가 언제 멈출지 모른다
□ 관련 파일 / 오류 / 문서  ← "전체 저장소"가 아니라 "관련"
□ 현재 상태             ← git status, 실패한 테스트
□ 적용할 규칙과 제한      ← rules.md / AGENTS.md
□ 이미 실패한 시도       ← 같은 삽질 반복 방지
□ 검증 방법             ← 어떻게 확인할 것인가
□ 출처와 버전           ← 문서가 언제 것인지
```

### 6-4. 지식(Knowledge) / 메모리(Memory) / 스킬(Skill) / 규칙(Rule) 구분 🟢

| 개념 | 정의 | 수명 | 택가이 대응 |
|---|---|---|---|
| **Knowledge** | 지금 과업에 검색·참조할 사실 | 과업 단위 | 지식화(.md), `knowledge_search` |
| **Memory** | 과업을 넘어 지속되는 정보 | 세션 넘김 | 택가이웹 개인화 메모리 |
| **Skill** | 반복 가능한 작업 **절차** | 영구·이식 가능 | SKILLS |
| **Rule** | 허용/금지/승인 같은 **행동 제약** | 영구·강제 | rules.md, permissions.yaml |

> **가장 많이 나오는 오해**: "지식화하면 모델이 학습되나요?"
> **답**: 아니다. 가중치는 안 바뀐다. **문서를 파싱해서 검색 가능한 형태로 저장했다가, 필요할 때 대화 맥락에 넣어주는 것**이다. 파인튜닝과 완전히 다르다. (sbti2·sbti3의 "지식화" 슬라이드에 이 한 줄을 넣으면 오해가 사라진다.)

### 6-5. 에이전트 메모리 프레임워크 (알아만 둘 것) 🟡

- **Letta (구 MemGPT)** — 메모리를 OS 가상메모리처럼: core(항상 컨텍스트=RAM) / archival(외부 검색=디스크) / recall(대화이력). 에이전트가 **스스로 메모리 관리 함수를 호출**한다.
- **Mem0** — 기존 프레임워크에 얹는 메모리 레이어.
- 강의에서는 "이런 게 있다" 수준. 코딩 에이전트 실무에서는 **파일/저장소가 여전히 최고의 메모리**라고 말하는 게 정직하다.

## 7. 멀티에이전트 — sbti2 MAS 슬라이드 심화 + 반론 무장

### 7-1. 4가지 표준 패턴 🟢

| 패턴 | 구조 | 언제 |
|---|---|---|
| **Sequential (파이프라인)** | A→B→C, 각 단계가 다음에 전달 | 단계가 명확할 때 |
| **Concurrent (병렬)** | 동시에 실행 후 결과 취합 | **탐색·검색·비교** |
| **Hierarchical (오케스트레이터-워커)** | 매니저가 분해→위임→통합 | 큰 과업 분해 |
| **Handoff** | 제어권을 전문가에게 넘김 | 도메인 라우팅 |

**당신 sbti2 슬라이드의 "리뷰 / 비교 / 찾기" 3전략은 각각 Sequential(작성→검토), Concurrent(두 관점 병렬), Concurrent(분할 탐색)에 정확히 매핑된다.** 이 대응표를 말해주면 자체 제품이 업계 표준 패턴 위에 있다는 게 즉시 전달된다.

### 7-2. 멀티에이전트의 비용 (반드시 같이 가르쳐야 정직하다)

| 이득 | 비용 |
|---|---|
| 독립 탐색 병렬화 | 토큰·지연 증가 (에이전트 수만큼 곱셈) |
| 다른 관점의 리뷰 | 같은 조사 중복 |
| 도메인 전문화 | 지시·완료기준 유실 |
| 작업 격리 | 같은 파일 충돌 |
| | **권한·공격면 증가** |
| | **컨텍스트 오버플로 — 오케스트레이터가 워커 결과를 다 받으면 4개 이상에서 창이 자주 넘친다** 🟡 |

> **강의 문장**: *"멀티에이전트는 '많을수록 좋다'가 아닙니다. **하나의 에이전트나 워크플로보다 측정 가능한 이점이 있을 때만** 켭니다. 저희 제품이 하네스가 요청을 판정한 뒤에 MAS를 켜는 이유가 그겁니다."*
> — 이 말을 하면 당신 슬라이드의 "하네스가 요청 판정 → 전략 선택" 설계가 **자랑이 아니라 절제**로 읽힌다. 훨씬 고급스럽다.

### 7-3. Anthropic 2026 Agentic Coding Trends Report — 멀티에이전트 관련 🟢

Anthropic 공식 리포트의 8개 트렌드 중 핵심:

1. **SDLC가 급변** — 온보딩이 주 → 시간 단위로 붕괴. 엔지니어 역할이 **구현자 → 오케스트레이터**
2. **단일 에이전트 → 조율된 팀** — 별도 컨텍스트 창에서 병렬 추론
3. **장시간 실행 에이전트가 완전한 시스템을 만든다** — 과업 시간축이 분 → 일/주
4. **인간 감독이 지능적으로 확장** — 에이전트가 **도움을 요청할 때를 배운다**
5. **새로운 표면·사용자로 확장** — COBOL·Fortran 등 레거시, 비개발자
6. **생산성이 소프트웨어 경제학을 바꾼다**
7. **비기술 부서로 확산**
8. **이중용도 위험 → 보안 우선 아키텍처**

**강의에 그대로 쓸 수 있는 숫자들** (전부 🟢, Anthropic 공식):
- 개발자는 업무의 **약 60%에 AI를 쓰지만, "완전 위임"이 가능하다고 답한 비율은 0~20%** ← **이번 강의 전체를 관통하는 최고의 수치.** "AI가 대체하냐"는 질문에 이 한 줄로 답이 끝난다.
- **AI 보조 작업의 약 27%는 원래 안 했을 일** — 대시보드, 실험, 사소한 불편(papercut) 개선. 즉 생산성은 "같은 일을 빨리"보다 **"산출량 자체의 증가"** 로 나타난다.
- **Rakuten**: vLLM(1,250만 줄 규모 오픈소스)에서 특정 활성화벡터 추출 기법 구현을 **단일 실행 7시간 자율 작업**으로 완료, 참조 대비 **수치정확도 99.9%**.
- **TELUS**: 사내 AI 솔루션 13,000개 이상 생성, 엔지니어링 코드 **30% 빠르게 출시**, 누적 **50만 시간** 절감(상호작용당 평균 40분).
- **Zapier**: 전사 AI 채택률 89%, 사내 배포 에이전트 800개 이상.
- **CRED**(인도 핀테크, 1,500만 사용자): 개발 전 주기에 Claude Code 적용 → **실행 속도 2배**. "사람을 빼서가 아니라 개발자를 더 높은 가치 업무로 옮겨서."

> 금융 청중에게는 **CRED 사례**가 가장 잘 먹힌다. 규제 산업 + 금융 + 품질 유지 + 2배. sbti2의 "금융업계 1위" 슬라이드 바로 앞에 놓으면 좋다.

### 7-4. Agent Teams — 2026년의 새 단어 🟡

Claude Code의 **Agent Teams**: 한 세션이 **팀장**이 되어 독립 팀원 에이전트를 띄우고, 팀원들이 **서로 직접 통신하고 작업목록을 공유하며 자율 조율**한다. 기존 서브에이전트(팀장만 통신)보다 한 단계 위.

**당신 슬라이드 보강**: sbti2의 "멀티세션 vs 멀티에이전트" 2단 구분에 **3단계**를 추가하면 최신이 된다.

```
1단계  멀티세션   — 창 여러 개. 사람이 조율.
2단계  서브에이전트 — 한 세션 안. 오케스트레이터만 통신. (택가이 현재)
3단계  에이전트 팀  — 팀원끼리 직접 통신·작업목록 공유·자율조율. (업계 최신)
```
이 표 하나로 "우리 위치와 다음 로드맵"이 동시에 설명된다.

## 8. 확장 규격 — MCP · Skills · AGENTS.md · A2A

### 8-1. 🚨 MCP는 2026-07-28에 대규모로 바뀌었다 (강의 이틀 전!) 🟢

**이건 이번 조사에서 가장 시의성 높은 발견이다.** 슬라이드에 MCP가 3번 등장하는데, 스펙이 **어제 그제 수준으로** 크게 바뀌었다.

**2026-07-28 스펙 — 주요 변경**
- **스테이트리스 전환**: `initialize` / `notifications/initialized` 핸드셰이크 **제거**. `Mcp-Session-Id` 헤더 **제거**. → 표준 로드밸런서 뒤에 세션 저장소 없이 배포 가능.
- **MRTR (Multi Round-Trip Requests)**: 도구가 실행 중간에 사용자 입력(확인·누락 인자)을 요구할 수 있게 `resultType: "input_required"` 도입. 서버가 스트림을 열어둘 필요 없음.
- **헤더 기반 라우팅**: `Mcp-Method`, `Mcp-Name` HTTP 헤더 필수. → **게이트웨이/WAF가 본문 파싱 없이 라우팅·인가 가능**.
- **캐시 가능한 list 결과**: `ttlMs`, `cacheScope`.
- **인가 강화**: RFC 9207 issuer 검증 필수, **DCR → CIMD(Client ID Metadata Documents)**, 자격증명을 발급 인가서버에 바인딩.
- **확장 프레임워크 공식화**: Tasks가 `io.modelcontextprotocol/tasks` 확장으로 이동. MCP Apps, EMA(Enterprise Managed Authorization)와 나란히.
- **폐기 예정**: Roots, Sampling, Logging (최소 12개월 지원 창), 레거시 HTTP+SSE 전송.
- SDK: TypeScript/Python/Go/C# 지원, Rust는 베타.

> **강의에서 이걸 말하면 즉시 "이 사람 진짜 최신이다"가 된다.**
> 문장: *"참고로 MCP 스펙은 **바로 어제(7월 28일)** 상당히 크게 바뀌었습니다. 세션 개념이 프로토콜에서 빠지고 스테이트리스가 됐어요. 그래서 **MCP 얘기를 할 때는 반드시 버전을 붙여서** 하셔야 합니다. 'MCP가 이렇다'가 아니라 '2026-07-28 스펙 기준으로 이렇다'로요."*
> **금융권 관점의 실익도 크다**: 헤더 라우팅 + CIMD + EMA 확장은 **사내 MCP 게이트웨이에서 정책을 강제하기 훨씬 쉬워졌다**는 뜻이다. 사내 MCP 플랫폼 계획이 있다면 이건 호재다.

### 8-2. MCP 기본 구조 (변하지 않는 부분) 🟢

- **Host**: 사용자·모델·정책을 조정하는 애플리케이션 (택가이코드)
- **Client**: host가 서버 하나와 유지하는 연결
- **Server**: resources / prompts / tools 를 제공
- **전송**: 로컬 프로세스(stdio) / 원격(Streamable HTTP)
- **한 줄 정의**: *MCP는 에이전트가 **내부 도구·데이터에 연결**하는 규격이고, A2A는 에이전트가 **다른 에이전트와 대화**하는 규격이다.*

## 9. 실행 환경 — ADE, worktree, 샌드박스, 권한

### 9-1. ADE (Agent Development Environment) 🟡

sbti1에 이미 있는 개념. 정의를 정확히:

> **ADE = 여러 코딩 에이전트를 동시에, 각각 격리된 git worktree에서 돌리고, 한 화면에서 관제·비교·병합하는 작업환경.** IDE가 "코드를 쓰는 곳"이라면 ADE는 **"에이전트를 관리하는 곳"**이다.

**Orca**: MIT 라이선스 오픈소스 ADE. Claude Code / Codex / OpenCode / Cursor CLI / Grok 등을 병렬 worktree에서 실행. 분할 터미널, 파일 에디터, git 추적, 브라우저 제어, 모바일 컴패니언 앱, GitHub/Linear/Jira 연동. 2026년 3월 등장, 7월 기준 12,500+ 스타, YC 백. 🟡

### 9-2. git worktree — 이걸 꼭 가르쳐라 🟢

```bash
git worktree add ../feat-a -b feat-a    # 같은 저장소, 별도 작업 디렉터리 + 별도 브랜치
```
- **여러 에이전트가 같은 파일을 동시에 고치는 사고를 원천 차단**하는 가장 싸고 확실한 방법.
- sbti2 "멀티에이전트" 슬라이드에서 나올 최다 질문(*"같은 파일 동시에 건드리면요?"*)의 정답이 이것이다. 한 줄 명령어를 슬라이드에 넣어라.

### 9-3. 샌드박싱 5단계 🟡

| 계층 | 기술 | 격리 강도 | 오버헤드 |
|---|---|---|---|
| OS 프로세스 샌드박스 | macOS **Seatbelt(sandbox-exec)**, Linux **bubblewrap**, Landlock+Seccomp | 중 | 최소 |
| 유저스페이스 커널 | gVisor | 중상 | 낮음 |
| microVM | Firecracker | 상 | 중 |
| dev container | Docker/devcontainer | 중 | 중 |
| 전체 VM | — | 최상 | 높음 |

- Claude Code는 Linux에서 bubblewrap, macOS에서 Seatbelt를 사용(**기본 비활성**). 🟡
- 실무 원칙: **프로젝트 디렉터리만 마운트(홈 디렉터리 절대 금지), root로 실행 금지, 경로 기반 allowlist 대신 콘텐츠 해시 검증**(에이전트가 경로 우회를 찾아낸 사례 있음).
- 신뢰할 수 없는 입력 + 대규모 실행이면 **최소 microVM**, 로컬 개발자 도구면 OS 프리미티브로 충분.

### 9-4. 권한 모델 🟢

표준화되어 가는 3단 모델: **allow / ask / deny**

Claude Code 기준 5개 모드(개념 참고용): default(위험한 건 물어봄) / acceptEdits(파일수정 자동승인, 셸은 물어봄) / plan(읽기전용) / dontAsk / bypassPermissions(완전 격리된 CI 전용).
**PreToolUse 훅**으로 도구 호출을 프로그램적으로 승인·거부 → 안전장치를 끄지 않고 자동화.

> **택가이코드 대응**: sbti3의 TOGGLE / ASK / OFF(`permissions.yaml`의 deny) 3단이 정확히 이 모델이다. 여기에 **"읽기 도구와 쓰기 도구를 분리하라"** 는 원칙 한 줄만 더 넣으면 보안팀이 좋아한다.

### 9-5. cmux / tmux 멀티터미널

sbti1에 있는 내용. 개념: **에이전트가 오래 도는 동안 사람이 놀지 않게 하는 것.** 병렬화의 이득 대부분은 모델이 아니라 **사람의 대기시간 제거**에서 온다. 이 프레이밍이 청중에게 훨씬 잘 꽂힌다.

### 10-3. 강사의 안전한 통합 서술 (이 문단을 외워라)

> "AI 코딩의 효과는 **과업 구조, 개발자 숙련도, 저장소 맥락, 사용 방식, 무엇을 측정하는가**에 따라 달라집니다.
> 산출량은 대체로 늘어납니다. 하지만 **'많이 나왔다'가 '잘 나왔다'는 아닙니다.**
> Anthropic 자체 연구에서도 개발자들은 업무의 60%에 AI를 쓰지만, **완전히 맡길 수 있다고 답한 비율은 0~20%**였습니다.
> 그래서 오늘 우리가 볼 것은 **결과 코드가 아니라 — 설명, diff, 테스트, 그리고 AI 없이 디버깅할 수 있는가**입니다."

### 10-4. METR Time Horizon (에이전트 능력 성장률) 🟢

- 정의: 모델이 **50% 성공률로 해내는 과업의 "인간 기준 소요시간"**.

- 2026-01 Time Horizon 1.1: 과제를 34% 확대(228개), 8시간 이상 과제를 2배(31개)로 늘려 신뢰구간 개선.
- **강의 활용**: "에이전트가 몇 시간짜리 일을 하냐"가 이 분야의 실질 지표다. Anthropic 리포트의 "분 → 일/주" 예측, OpenAI의 "6시간 단일 실행", Rakuten의 "7시간 자율"이 전부 같은 곡선 위의 점이다. **이 그래프 하나가 sbti1의 도입부로 완벽하다.**

### 10-5. Vibe coding → Agentic engineering 🟢

- Karpathy가 2025-02 "vibe coding"을 만들었고, **정확히 1년 뒤인 2026-02에 "agentic engineering"으로 개명**하며 자기가 만든 단어와 거리를 뒀다.
- 원뜻은 **주말 버리는 프로젝트**용이었지 프로덕션용이 아니었다.
- 2026년 현재 이 단어는 3갈래로 찢어졌다: ①원뜻(리뷰 없음) ②확산된 뜻(AI 보조 개발 전반) ③비하(검증 없이 배포한 코드).
- **강의 문장**: *"'바이브 코딩'이란 말은 만든 사람이 1년 만에 철회했습니다. 오늘 우리가 배우는 건 바이브 코딩이 아니라 **에이전틱 엔지니어링** — 검증이 붙은 위임입니다."*

## 11. 보안 — 금융권 강의의 진짜 승부처

### 11-1. Prompt Injection과 Lethal Trifecta 🟢

**근본 원인 (이 문장이 핵심)**: LLM은 **신뢰할 수 있는 명령과 신뢰할 수 없는 데이터를 구분할 방법이 구조적으로 없다.** 둘 다 같은 토큰 스트림으로 들어온다. 입력 필터링과 최소권한은 위험을 줄이지만 **근본 결함은 없애지 못한다.**

**Lethal Trifecta** (Simon Willison, 2025) — 셋이 동시에 있으면 **악용은 시간 문제**:
1. **비공개 데이터 접근** (사내 코드, DB, 문서)
2. **신뢰할 수 없는 토큰 노출** (이슈 코멘트, README, 웹, 의존성, MCP 도구 설명)
3. **유출 경로** (외부 HTTP 요청, 이미지 렌더링, 링크 생성, API 호출)

> **금융권 슬라이드용 문장**: *"에이전트에게 사내 데이터를 주면서, 외부 텍스트를 읽게 하고, 동시에 외부로 나갈 수 있게 하면 — **셋 중 하나는 반드시 끊어야 합니다.** 저희 내부망 구조는 3번(유출 경로)이 물리적으로 끊겨 있다는 게 가장 큰 보안 자산입니다."*
> **이게 택가이코드 온프렘 전략의 보안 논리를 가장 우아하게 설명하는 방법이다. 강력 추천.**

### 11-2. 코딩 에이전트에 실제로 오는 공격

| 공격 | 설명 |
|---|---|
| **간접 프롬프트 인젝션** | 저장소 README·이슈·주석·의존성 문서에 명령을 심어둠 |
| **MCP Tool Poisoning** | 악성 MCP 서버의 **도구 설명(description)** 자체에 지시를 심음. 사용자는 도구 이름만 본다 |
| **Rug Pull** | 승인받은 뒤 서버가 도구 정의를 바꿈 |
| **Confused Deputy** | 에이전트의 정당한 권한을 빌려 공격자가 원하는 행동 유도 |
| **Slopsquatting** | 아래 별도 |

**MCP 안전수칙 (슬라이드용 6줄)**
1. 로컬 MCP 서버는 **설치 프로그램처럼** 취급하라
2. 신뢰한 서버만 allowlist
3. **`readOnlyHint` 같은 annotation은 힌트일 뿐 보안 통제가 아니다** ← 자주 나오는 함정 질문
4. 자격증명을 프롬프트·컨텍스트·로그에 넣지 마라
5. 원격 토큰은 audience·scope를 좁혀라
6. **읽기 도구와 쓰기 도구를 분리**하고, 쓰기·삭제·전송·관리는 별도 승인

### 11-3. Slopsquatting (패키지 환각) 🟢🟡

- 정의: LLM이 **존재하지 않는 패키지 이름을 환각**하면, 공격자가 그 이름을 **미리 등록**해 놓고 기다린다.
- 환각률: 오픈소스 모델 평균 **21.7%**, 상용 모델 평균 **5.2%**. 🟡
- **가장 위험한 특성 — 재현성**: 같은 프롬프트를 10번 돌렸을 때 **환각 패키지 이름의 43%가 매번 똑같이** 나왔다. 즉 공격자가 **예측 가능**하다.
- 2026년 사례: 1월 npm `react-codeshift` PoC, 2월 Clinejection(CI/CD 파이프라인 내 에이전트로 위험 확대). 🟡
- **자율 에이전트가 붙으면 위험 등급이 달라진다**: 예전엔 사람이 "설치할까?" 하는 체크포인트가 있었지만, 에이전트는 그냥 설치한다.
- **실습 규칙**: 패키지 존재·공식 레지스트리·owner·버전·라이선스·취약점·유지상태를 확인하기 전엔 설치 금지. **이걸 sbti1 실습의 "일부러 심은 잘못된 제안"으로 쓰면 최고의 교육 소재다.**

### 11-4. OpenClaw 사례 — "자율 에이전트를 함부로 깔면 이렇게 된다" 🟡

# C. 키워드 사전

## 13. 130+ 용어 한 줄 정의

청중이 던지는 단어를 즉시 받아치기 위한 사전. **굵은 글씨는 강의 중 실제로 나올 확률이 높은 것.**

### 13-1. 에이전트 기본
- **Agent** — 모델이 도구·순서·분기·중단을 동적으로 결정하며 목표를 향해 반복 실행하는 시스템
- **Agentic loop** — 계획→도구→관찰→판단의 반복
- **Tool calling / Function calling** — 모델이 "이 도구를 이 인자로" 라는 구조화 출력을 내는 것. 실행은 하네스가 함
- **ReAct** — Reasoning + Acting 을 번갈아 하는 고전 패턴
- **Scaffolding** — 모델 주위의 코드. 하네스의 옛 이름에 가까움
- **Harness** — 모델을 제외한 전부(도구·상태·메모리·권한·검증·관측)
- **Orchestrator** — 과업을 분해해 하위 에이전트에 위임하고 결과를 통합하는 상위 에이전트
- **Subagent** — 독립 컨텍스트와 도구 집합을 가진 하위 에이전트
- **Agent Teams** — 팀원 에이전트끼리 직접 통신·작업목록 공유·자율 조율하는 최신 형태
- **Handoff** — 제어권 자체를 다른 에이전트에 넘기는 방식
- **HITL (Human-in-the-loop)** — 사람 승인 지점을 루프에 넣는 것
- **Task horizon** — 에이전트가 자율로 감당하는 과업의 시간 길이
- **Autonomy level** — 제안만 / 편집 / 실행 / 배포 — 어디까지 허용하는가
- **Background agent** — 비동기로 돌다가 완료 시 알림/PR로 회수
- **Cloud agent** — 원격 격리 샌드박스에서 저장소를 클론해 작업

### 13-2. 컨텍스트
- **Context window** — 한 번에 모델이 볼 수 있는 토큰 한도
- **Effective context** — 실제로 정확도가 유지되는 구간. 광고값보다 훨씬 작다
- **Context engineering** — 창에 무엇을 넣을지 설계하는 규율
- **Context rot** — 무관한 내용이 쌓여 조용히 정확도가 떨어지는 현상
- **Compaction** — 대화를 요약해 새 창으로 이어붙이기
- **Progressive disclosure** — 이름·설명만 먼저 보여주고 필요할 때 본문을 로드
- **Prompt caching** — 반복되는 앞부분을 캐시해 최대 90% 절감
- **KV cache** — 어텐션 키/값 재사용. 추론 속도의 핵심
- **Prefix caching / RadixAttention** — 공유 프리픽스 재사용(SGLang). 에이전트 워크로드에 특히 유효
- **RAG** — 검색해서 컨텍스트에 붙이는 전처리형 방식
- **Agentic search** — 에이전트가 grep·읽기·목록을 도구로 써서 능동 탐색
- **Embedding / Vector DB / Chunking / Reranking** — 전통 RAG 부품들. 코드 검색에서는 퇴조 중
- **Memory (core / archival / recall)** — Letta식 3계층 메모리
- **Knowledge / Skill / Rule** — 사실 / 절차 / 제약 (6-4 참조)
- **AGENTS.md / CLAUDE.md / .techai.md / rules.md** — 에이전트에게 주는 프로젝트 지침 파일
- **SKILL.md** — Agent Skills 표준의 스킬 정의 파일

### 13-3. 모델
- **LLM / SLM** — 대형 / 소형 언어모델
- **MoE (Mixture of Experts)** — 토큰마다 일부 전문가만 활성화. 큰 총파라미터, 작은 활성 파라미터
- **Dense** — 전 파라미터를 매번 사용
- **Open-weight vs Open-source** — 가중치 공개 ≠ 학습데이터·코드 공개. **온프렘 가능 여부는 open-weight로 결정**
- **Quantization (FP8 / INT8 / INT4 / GGUF / AWQ)** — 정밀도를 낮춰 메모리·속도 확보
- **Distillation** — 큰 모델의 행동을 작은 모델에 옮김
- **LoRA / PEFT / Fine-tuning** — 부분 가중치 조정. **지식화와 혼동 금지**
- **RLHF / RLAIF / RLVR** — 사람/AI/**검증가능한 보상**으로 강화학습. RLVR이 코드·수학 성능의 주 동력
- **Reasoning model** — 답하기 전 생각 토큰을 태우는 모델
- **Test-time compute** — 추론 시점에 계산을 더 써서 성능을 올리는 것
- **Thinking budget** — 생각 토큰 상한 파라미터
- **Interleaved thinking** — 도구 호출 사이사이에 생각을 끼워 넣는 것
- **Speculative decoding** — 작은 모델이 초안, 큰 모델이 검증 → 속도 향상
- **Structured output / JSON schema / Constrained decoding** — 출력 형식을 강제
- **Temperature / top-p** — 샘플링 무작위성
- **Hallucination / Grounding** — 근거 없는 생성 / 근거에 묶기
- **Knowledge cutoff** — 학습 데이터의 시점 한계
- **Multimodal** — 텍스트+이미지+오디오

### 13-4. 프로토콜·규격

## 15. 예상 난문 Top 20 + 답변 스크립트

**Q1. AI가 개발자를 대체하나요?**
> Anthropic 자체 연구에서 개발자는 업무의 약 60%에 AI를 쓰지만 **"완전히 위임할 수 있다"고 답한 비율은 0~20%**였습니다. 대체가 아니라 **역할 이동** — 구현자에서 오케스트레이터로. 다만 **"코드를 안 읽어도 되는 사람"은 확실히 줄어듭니다.**

**Q2. 그럼 주니어는 어떻게 하나요?** *(가장 어려운 질문. 반드시 준비)*
> 정직하게 말씀드리면 데이터가 경고를 보냅니다. Anthropic이 주니어 52명으로 한 무작위 실험에서, AI를 쓴 그룹의 이해도 퀴즈 점수가 **50점, 손으로 짠 그룹이 67점**이었습니다. **디버깅 문항에서 격차가 가장 컸습니다.** 속도 이득은 2분 남짓이었고요.
> 대응은 AI를 안 쓰는 게 아니라 **쓰는 방식을 바꾸는 것**입니다. 코드를 받는 데서 멈추지 말고 **"왜 이렇게 했는지" 되묻기**, 에러를 스스로 한 번 만나보기, 학습·설명 모드 쓰기. 오늘 실습에서 **AI 없이 변경 내용을 60초 안에 설명하기**를 완료 기준에 넣은 이유입니다.

**Q3. 우리 내부망 모델은 GPT/Claude보다 약한데 의미가 있나요?**
> 세 가지로 답합니다. ①**Agent = Model + Harness**입니다. LangChain은 모델을 안 바꾸고 하네스만 고쳐 Terminal-Bench 30위→5위로 갔습니다. ②오픈웨이트 격차가 빠르게 좁혀지고 있습니다. ③그리고 **외부 모델은 애초에 우리 코드를 볼 수 없습니다.** 볼 수 없는 최고 성능보다 볼 수 있는 충분한 성능이 낫습니다.

**Q4. 벤치마크 1등 모델로 바꾸면 안 되나요?**
> 리더보드 숫자는 모델만의 점수가 아니라 **모델+하네스+채점방식의 합산**입니다. 같은 모델이 어디서 재느냐에 따라 10점 넘게 흔들립니다. 실제로 이번에 조사해보니 같은 벤치마크 상위값이 출처별로 76%~96%까지 벌어졌습니다. 봐야 할 건 순위가 아니라 **우리 코드베이스에서의 재현 가능한 성공률**입니다.

**Q5. 멀티에이전트는 항상 좋은가요?**
> 아닙니다. 토큰·지연이 에이전트 수만큼 곱해지고, 중복 조사, 지시 유실, 파일 충돌, **권한과 공격면 확대**가 따라옵니다. 특히 오케스트레이터가 워커 결과를 다 받으면 **4개 이상에서 컨텍스트가 자주 넘칩니다.** **단일 에이전트보다 측정 가능한 이점이 있을 때만** 켭니다.

**Q6. 같은 파일을 여러 에이전트가 동시에 고치면요?**
> `git worktree add ../feat-a -b feat-a` — 같은 저장소의 별도 작업 디렉터리를 하나씩 줍니다. 담당 범위를 나누거나 브랜치/worktree로 격리하고, **하나의 작업을 여러 에이전트가 동시에 쓰게 두지 않습니다.**

**Q7. 지식화하면 모델이 학습되나요?**
> 아닙니다. 가중치는 안 바뀝니다. 문서를 파싱해 검색 가능한 형태로 저장했다가 **필요할 때 대화 맥락에 넣는 것**입니다. 파인튜닝과는 완전히 다릅니다.

**Q8. RAG/벡터DB는 안 쓰나요?**
> 코드 검색에서는 업계가 이미 방향을 틀었습니다. **Claude Code는 2025년 5월에 벡터 검색을 걷어내고 grep으로 갔고**, 결과가 훨씬 좋았습니다. 인덱스 동기화도 없고 **항상 현재 파일 상태**를 봅니다. 다만 **문서·가이드는 여전히 검색형 지식**이 맞습니다. 코드는 grep, 문서는 지식화 — 이렇게 나눕니다.

**Q9. MCP 서버 추가하면 바로 안전한가요?**
> 아닙니다. **로컬 MCP 서버는 설치 프로그램처럼 취급**해야 합니다. 출처·owner·권한·데이터·토큰·도구 범위·로그·프롬프트 인젝션 가능성을 봐야 합니다. 참고로 MCP 스펙은 **어제(7/28) 크게 개정**됐습니다. 세션이 프로토콜에서 빠지고 스테이트리스가 됐어요. MCP 얘기는 반드시 버전을 붙여서 하셔야 합니다.

**Q10. `readOnlyHint` 있으면 읽기 전용 아닌가요?**
> 스펙상 annotation은 **힌트이지 보안 통제가 아닙니다.** 신뢰한 서버와 실제 인가가 있어야 합니다.

**Q11. 프롬프트 인젝션이 코딩에서도 생기나요?**
> 생깁니다. 저장소 README, 이슈, 의존성 문서, **MCP 도구 설명**, 검색 결과가 모델에 행동을 지시할 수 있습니다. 근본 원인은 **LLM이 명령과 데이터를 구조적으로 구분할 수 없다**는 겁니다. 그래서 lethal trifecta — 비공개 데이터 + 신뢰 못할 텍스트 + 유출 경로 — **셋 중 하나는 끊어야** 합니다.

**Q12. AI가 알려준 패키지 설치해도 되나요?**
> 확인 전엔 안 됩니다. 오픈소스 모델은 평균 21.7%, 상용 모델도 5.2%가 **없는 패키지를 지어냅니다.** 더 무서운 건 재현성입니다 — 같은 프롬프트 10번에 **환각 이름의 43%가 매번 똑같이** 나옵니다. 공격자가 그 이름을 미리 등록해둡니다. 존재·레지스트리·owner·버전·라이선스·취약점을 확인하고 설치하세요.

**Q13. 생산성이 정말 오르나요? 반대 연구도 있던데요.**
> 둘 다 맞습니다. 산출량은 대체로 늘어납니다. 동시에 **METR 실험에서는 숙련 개발자가 익숙한 저장소에서 오히려 19% 느려졌고**, 본인들은 빨라졌다고 느꼈습니다. DORA 2026은 AI를 **증폭기**라고 부릅니다 — 개인 효과성도 올리고 **전달 불안정성도 올립니다.** 그래서 도입은 도구 배포가 아니라 **검증 체계 설계**입니다.

**Q14. 코드 품질이 떨어진다던데요?**
> 그 신호는 실재합니다. 리팩터링 비중이 줄고 기술부채가 늘었다는 대규모 분석이 있습니다. 다만 **원인은 AI가 아니라 "검증 없는 속도"** 입니다. 그래서 PR 크기 상한, 테스트 필수, PR 리뷰 게이트, 린터로 아키텍처 강제 — 이런 하네스가 같이 가야 합니다. OpenAI가 100만 줄을 만들 때 한 일이 정확히 그것이었습니다.

**Q15. 우리 코드가 외부로 나가나요?**
> 택가이코드는 내부망 온프렘 구성입니다. 다만 정확한 로그 저장 범위·보존기간은 **제품/보안 담당 기준으로 답변드리겠습니다.** (※ 강사 주: 이 항목은 절대 추측 금지. 사전에 실제 정책 확인 필수)

**Q16. 도구가 37개인가요 50개 이상인가요?**
> 제품 버전에 따라 inventory가 다릅니다. 교육에 배포한 빌드에서 직접 목록을 출력해 **기준일과 함께** 말씀드리겠습니다.

**Q17. Cursor/Claude Code 대비 어떤가요?**
> 표면과 관리체계가 다릅니다. 비교는 브랜드가 아니라 **①어디서 실행되고 ②무엇을 볼 수 있고 ③무엇을 실행할 권한이 있고 ④누가 감사할 수 있는가** 로 하셔야 합니다. 4번이 금융권에서는 결정적입니다.

**Q18. Skill과 MCP 차이는?**
> Skill은 **반복 가능한 작업 절차**이고, MCP는 **외부 데이터·도구를 연결하는 프로토콜**입니다. 스킬은 "어떻게 하는지", MCP는 "무엇에 닿는지"입니다.

**Q19. 앞으로 뭐가 더 옵니까?**
> 세 방향입니다. ①**과업 시간축의 연장** — 분에서 시간, 시간에서 일로. METR 측정에서 4~7개월마다 2배입니다. ②**감독의 지능화** — 에이전트가 스스로 "이건 사람에게 물어야 한다"를 판단. ③**개발자 밖으로 확장** — 데스크톱·비개발 직군. 저희 데스크톱 로드맵이 3번입니다.

**Q20. 오늘부터 뭘 하면 되나요?**
> 세 개만 하세요. ① 저장소에 **AGENTS.md(또는 .techai.md)를 100줄 이내 목차로** 만들기. ② **작은 diff + 테스트**를 기본 리듬으로. ③ 에이전트가 같은 실수를 하면 **프롬프트를 고치지 말고 환경(린터·테스트·규칙)을 고치기.** 세 번째가 하네스 엔지니어링의 전부입니다.
