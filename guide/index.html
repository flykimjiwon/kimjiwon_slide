4. 두 조사가 일치한 것 — 안심하고 말해도 되는 것

교차검증에서 양쪽이 독립적으로 같은 결론에 도달한 항목이다. 신뢰도가 가장 높다.

  1. 하네스가 모델보다 중요하다. 양쪽 모두 OpenAI 하네스 엔지니어링 사례를 1차 출처로 인용. 단, "10배"를 일반 법칙으로 옮기지 말 것.
  2. 멀티에이전트는 항상 우수하지 않다. 독립적 분해·검증 이익이 비용·충돌·상관오류보다 클 때만.
  3. 긴 컨텍스트는 RAG·메모리를 대체하지 않는다. relevance·freshness·권한·인용·비용 문제가 남는다.
  4. 지식화는 학습이 아니다. 파싱·검색·컨텍스트 주입이다.
  5. MCP 연결은 신뢰가 아니다. readOnlyHint 등 annotation은 힌트지 보안 통제가 아니다.
  6. 프롬프트만으로 인젝션을 막을 수 없다. 최소권한·샌드박스·승인·egress 통제가 필요하다.
  7. 생산성 증거는 양방향이다. METR의 19% 감속, Anthropic 스킬형성 연구, DORA의 "증폭기" 결론을 반드시 함께 제시.
  8. 에이전트가 멈춘 것은 완료가 아니다. acceptance evidence를 본다.
  9. 워크플로와 에이전트를 구분해서 가르쳐야 한다. 규정·감사가 걸린 곳은 워크플로.
  10. 수업 성공의 기준은 산출물이 아니라 설명 능력이다. 학생이 AI 없이 diff와 위험을 설명할 수 있어야 한다.

4. 에이전트 루프 — 원리 (sbti1 1번 슬라이드 심화)

4-1. 루프의 정체

핵심은 LLM은 아무것도 하지 않는다는 것. LLM은 "이 도구를 이 인자로 부르겠다"는 구조화된 출력을 뱉을 뿐이고, 실제 실행은 하네스가 한다. sbti2의 285~310행("AI가 도구를 쓰는 순서")이 정확히 이걸 그리고 있다. 여기에 한 문장만 더 붙이면 완성된다:

"모델은 '무엇을 하고 싶다'고 말할 뿐이고, 실제로 할지 말지는 하네스가 결정합니다. 그래서 보안은 모델이 아니라 하네스에 겁니다."

4-2. Workflow vs Agent (반드시 구분해서 가르칠 것)

금융권 강의에서 특히 중요: "전부 에이전트로 하자"가 아니라 "규정이 걸린 곳은 워크플로, 탐색이 필요한 곳은 에이전트" 가 정답이라고 못박아라. 이 한 마디로 컴플라이언스 쪽 청중의 신뢰를 얻는다.

4-3. 검색 방식의 대전환 — 벡터 RAG → 에이전틱 검색 A

이건 강의에서 반드시 다뤄라. 대부분의 청중이 "AI 코딩 = RAG/벡터DB"라고 잘못 알고 있다.

  • 2025년 5월, Claude Code는 벡터 검색을 걷어내고 grep으로 갈아탔다. 임베딩 파이프라인·로컬 벡터DB·청킹 휴리스틱을 전부 제거. 결과는 "압도적으로 더 좋았다".
  • 이후 Cursor, Windsurf, Cline, Devin, Amp 등이 유사한 방향으로 이동. B
  • 이유: 코드는 정확한 식별자로 찾는 게 맞다. 인덱스 동기화 문제도 없고, 항상 현재 파일 상태를 본다.
  • 논문 근거: "Is Grep All You Need?"(arXiv 2605.15184) — inline 전달 방식에서는 모든 하네스-모델 조합에서 lexical(grep)이 dense retrieval보다 일관되게 강했다. 단, 노이즈가 커지면 교차점이 생기고 그 교차점은 하네스마다 다르다.
  • Amazon Science(AAAI 2026): 에이전틱 키워드 검색이 벡터 스토어 없이 RAG faithfulness의 94.5% 도달. B

당신 제품과의 연결: 택가이코드의 grep_search / glob_search / file_read / knowledge_search 조합(sbti3의 37 tools 슬라이드)이 바로 이 최신 설계다. "우리는 유행 지난 RAG를 안 쓴다"가 아니라 "업계가 2025년에 벡터를 버리고 온 방향에 우리가 이미 서 있다" 로 말하면 훨씬 강하다. 단, 지식화(문서 파싱→.md→검색)는 여전히 유효하다. 코드는 grep, 문서·가이드는 검색형 지식이 맞다. 이 구분을 명확히 하라.

5-3. OpenAI의 실제 하네스 실무 (강의에서 그대로 인용 가능) A

OpenAI가 코드 한 줄 손으로 안 쓰고 100만 줄을 만든 방법:

  1. 점진적 공개(progressive disclosure) — AGENTS.md를 약 100줄의 목차로만 유지하고, 상세 지침은 docs/ 하위(design-docs, exec-plans, product-specs, references)로 분리. 원칙: "컨텍스트는 희소 자원이다."
  2. 기계적 강제 — 계층 의존 규칙(Types → Config → Repo → Service → Runtime → UI)을 린터로 차단. 에러 메시지에 수정 방법까지 적어서 그게 곧 에이전트의 컨텍스트가 되게 함.
  3. 저장소가 단일 진실 원천 — 설계문서·실행계획·기술부채 트래커를 전부 버전관리되는 마크다운으로.
  4. 피드백 루프 — worktree별 격리 인스턴스 기동, DOM 스냅샷·스크린샷 캡처, 로그/메트릭 질의 → 고침→재시작→재검증 반복.
  5. 기술부채 가비지 컬렉션 — 백그라운드 작업이 패턴 위반을 스캔해 리팩터링 PR을 자동 생성.

이 5개를 슬라이드 한 장으로 만들면 당신 강의에서 가장 실무적인 장면이 된다. 청중이 "우리 팀에서 당장 뭘 해야 하나"에 대한 답을 여기서 얻는다. AGENTS.md 100줄 목차 하나만으로도 강의가 기억된다.

6. 컨텍스트 엔지니어링 — "많이 넣으면 좋다"는 틀렸다

6-1. Context Rot (컨텍스트 부패) A

  • 정의: 관련 없는 도구 출력·낡은 중간상태·중복 재읽기가 쌓이면서 모델이 조용히 정확도를 잃는 현상.
  • 무서운 점: 에러가 안 난다. 그냥 신호에 덜 집중한다.
  • Chroma 연구(18개 프론티어 모델): 200K 창이 5만 토큰에서 이미 심각한 정확도 손실을 보일 수 있다. 1M 창이 1M을 신뢰성 있게 추론하지 못한다.
  • 실무 결론: 광고 컨텍스트(1M)가 아니라 실효 컨텍스트(대략 200~400K)로 설계하라. B
  • 특히: needle과 주변 텍스트가 의미적으로 비슷할수록 정확도가 급락한다. 길이보다 유사 방해자(distractor) 가 더 치명적이다.

6-2. Compaction (압축) A

  • 정의: 창이 차기 전에 대화를 요약해 새 창으로 이어붙이는 것.
  • Anthropic API에 compact_20260112(2026-04 기준 베타)가 있고, 임계값(최소 50K, 기본 150K), 커스텀 요약 프롬프트, 압축 후 일시정지 옵션 등을 제공. B
  • 실무: 압축은 무손실이 아니다. 압축 직후 에이전트가 "아까 정한 규칙"을 잊는 일이 흔하다. → 중요한 결정은 대화가 아니라 파일(저장소)에 적어라. 이게 OpenAI가 "repo가 단일 진실 원천"이라고 한 이유.

6-3. 좋은 컨텍스트의 구성 (강의 체크리스트)

6-4. 지식(Knowledge) / 메모리(Memory) / 스킬(Skill) / 규칙(Rule) 구분 A

개념정의수명택가이 대응

가장 많이 나오는 오해: "지식화하면 모델이 학습되나요?" 답: 아니다. 가중치는 안 바뀐다. 문서를 파싱해서 검색 가능한 형태로 저장했다가, 필요할 때 대화 맥락에 넣어주는 것이다. 파인튜닝과 완전히 다르다. (sbti2·sbti3의 "지식화" 슬라이드에 이 한 줄을 넣으면 오해가 사라진다.)

6-5. 에이전트 메모리 프레임워크 (알아만 둘 것) B

  • Letta (구 MemGPT) — 메모리를 OS 가상메모리처럼: core(항상 컨텍스트=RAM) / archival(외부 검색=디스크) / recall(대화이력). 에이전트가 스스로 메모리 관리 함수를 호출한다.
  • Mem0 — 기존 프레임워크에 얹는 메모리 레이어.
  • 강의에서는 "이런 게 있다" 수준. 코딩 에이전트 실무에서는 파일/저장소가 여전히 최고의 메모리라고 말하는 게 정직하다.

7-3. Anthropic 2026 Agentic Coding Trends Report — 멀티에이전트 관련 A

Anthropic 공식 리포트의 8개 트렌드 중 핵심:

  1. SDLC가 급변 — 온보딩이 주 → 시간 단위로 붕괴. 엔지니어 역할이 구현자 → 오케스트레이터
  2. 단일 에이전트 → 조율된 팀 — 별도 컨텍스트 창에서 병렬 추론
  3. 장시간 실행 에이전트가 완전한 시스템을 만든다 — 과업 시간축이 분 → 일/주
  4. 인간 감독이 지능적으로 확장 — 에이전트가 도움을 요청할 때를 배운다
  5. 새로운 표면·사용자로 확장 — COBOL·Fortran 등 레거시, 비개발자
  6. 생산성이 소프트웨어 경제학을 바꾼다
  7. 비기술 부서로 확산
  8. 이중용도 위험 → 보안 우선 아키텍처

강의에 그대로 쓸 수 있는 숫자들 (전부 A, Anthropic 공식):

  • 개발자는 업무의 약 60%에 AI를 쓰지만, "완전 위임"이 가능하다고 답한 비율은 0~20% ← 이번 강의 전체를 관통하는 최고의 수치. "AI가 대체하냐"는 질문에 이 한 줄로 답이 끝난다.
  • AI 보조 작업의 약 27%는 원래 안 했을 일 — 대시보드, 실험, 사소한 불편(papercut) 개선. 즉 생산성은 "같은 일을 빨리"보다 "산출량 자체의 증가" 로 나타난다.
  • Rakuten: vLLM(1,250만 줄 규모 오픈소스)에서 특정 활성화벡터 추출 기법 구현을 단일 실행 7시간 자율 작업으로 완료, 참조 대비 수치정확도 99.9%.
  • TELUS: 사내 AI 솔루션 13,000개 이상 생성, 엔지니어링 코드 30% 빠르게 출시, 누적 50만 시간 절감(상호작용당 평균 40분).
  • Zapier: 전사 AI 채택률 89%, 사내 배포 에이전트 800개 이상.
  • CRED(인도 핀테크, 1,500만 사용자): 개발 전 주기에 Claude Code 적용 → 실행 속도 2배. "사람을 빼서가 아니라 개발자를 더 높은 가치 업무로 옮겨서."

금융 청중에게는 CRED 사례가 가장 잘 먹힌다. 규제 산업 + 금융 + 품질 유지 + 2배. sbti2의 "금융업계 1위" 슬라이드 바로 앞에 놓으면 좋다.

  • 인가 강화: RFC 9207 issuer 검증 필수, DCR → CIMD(Client ID Metadata Documents), 자격증명을 발급 인가서버에 바인딩.
  • 확장 프레임워크 공식화: Tasks가 io.modelcontextprotocol/tasks 확장으로 이동. MCP Apps, EMA(Enterprise Managed Authorization)와 나란히.
  • 폐기 예정: Roots, Sampling, Logging (최소 12개월 지원 창), 레거시 HTTP+SSE 전송.
  • SDK: TypeScript/Python/Go/C# 지원, Rust는 베타.

강의에서 이걸 말하면 즉시 "이 사람 진짜 최신이다"가 된다. 문장: "참고로 MCP 스펙은 바로 어제(7월 28일) 상당히 크게 바뀌었습니다. 세션 개념이 프로토콜에서 빠지고 스테이트리스가 됐어요. 그래서 MCP 얘기를 할 때는 반드시 버전을 붙여서 하셔야 합니다. 'MCP가 이렇다'가 아니라 '2026-07-28 스펙 기준으로 이렇다'로요." 금융권 관점의 실익도 크다: 헤더 라우팅 + CIMD + EMA 확장은 사내 MCP 게이트웨이에서 정책을 강제하기 훨씬 쉬워졌다는 뜻이다. 사내 MCP 플랫폼 계획이 있다면 이건 호재다.

8-2. MCP 기본 구조 (변하지 않는 부분) A

  • Host: 사용자·모델·정책을 조정하는 애플리케이션 (택가이코드)

  • Server: resources / prompts / tools 를 제공

11. 보안 — 금융권 강의의 진짜 승부처

11-1. Prompt Injection과 Lethal Trifecta A

근본 원인 (이 문장이 핵심): LLM은 신뢰할 수 있는 명령과 신뢰할 수 없는 데이터를 구분할 방법이 구조적으로 없다. 둘 다 같은 토큰 스트림으로 들어온다. 입력 필터링과 최소권한은 위험을 줄이지만 근본 결함은 없애지 못한다.

Lethal Trifecta (Simon Willison, 2025) — 셋이 동시에 있으면 악용은 시간 문제:

  1. 비공개 데이터 접근 (사내 코드, DB, 문서)
  2. 신뢰할 수 없는 토큰 노출 (이슈 코멘트, README, 웹, 의존성, MCP 도구 설명)
  3. 유출 경로 (외부 HTTP 요청, 이미지 렌더링, 링크 생성, API 호출)

금융권 슬라이드용 문장: "에이전트에게 사내 데이터를 주면서, 외부 텍스트를 읽게 하고, 동시에 외부로 나갈 수 있게 하면 — 셋 중 하나는 반드시 끊어야 합니다. 저희 내부망 구조는 3번(유출 경로)이 물리적으로 끊겨 있다는 게 가장 큰 보안 자산입니다." 이게 택가이코드 온프렘 전략의 보안 논리를 가장 우아하게 설명하는 방법이다. 강력 추천.

11-3. Slopsquatting (패키지 환각) AB

  • 정의: LLM이 존재하지 않는 패키지 이름을 환각하면, 공격자가 그 이름을 미리 등록해 놓고 기다린다.

13. 130+ 용어 한 줄 정의

청중이 던지는 단어를 즉시 받아치기 위한 사전. 굵은 글씨는 강의 중 실제로 나올 확률이 높은 것.

13-1. 에이전트 기본

  • Agent — 모델이 도구·순서·분기·중단을 동적으로 결정하며 목표를 향해 반복 실행하는 시스템
  • Agentic loop — 계획→도구→관찰→판단의 반복
  • Tool calling / Function calling — 모델이 "이 도구를 이 인자로" 라는 구조화 출력을 내는 것. 실행은 하네스가 함
  • ReAct — Reasoning + Acting 을 번갈아 하는 고전 패턴
  • Scaffolding — 모델 주위의 코드. 하네스의 옛 이름에 가까움
  • Harness — 모델을 제외한 전부(도구·상태·메모리·권한·검증·관측)
  • Orchestrator — 과업을 분해해 하위 에이전트에 위임하고 결과를 통합하는 상위 에이전트
  • Subagent — 독립 컨텍스트와 도구 집합을 가진 하위 에이전트
  • Agent Teams — 팀원 에이전트끼리 직접 통신·작업목록 공유·자율 조율하는 최신 형태
  • Handoff — 제어권 자체를 다른 에이전트에 넘기는 방식
  • HITL (Human-in-the-loop) — 사람 승인 지점을 루프에 넣는 것
  • Task horizon — 에이전트가 자율로 감당하는 과업의 시간 길이
  • Autonomy level — 제안만 / 편집 / 실행 / 배포 — 어디까지 허용하는가
  • Background agent — 비동기로 돌다가 완료 시 알림/PR로 회수
  • Cloud agent — 원격 격리 샌드박스에서 저장소를 클론해 작업

15. 예상 난문 Top 20 + 답변 스크립트

Q1. AI가 개발자를 대체하나요?

Anthropic 자체 연구에서 개발자는 업무의 약 60%에 AI를 쓰지만 "완전히 위임할 수 있다"고 답한 비율은 0~20%였습니다. 대체가 아니라 역할 이동 — 구현자에서 오케스트레이터로. 다만 "코드를 안 읽어도 되는 사람"은 확실히 줄어듭니다.

Q2. 그럼 주니어는 어떻게 하나요? (가장 어려운 질문. 반드시 준비)

정직하게 말씀드리면 데이터가 경고를 보냅니다. Anthropic이 주니어 52명으로 한 무작위 실험에서, AI를 쓴 그룹의 이해도 퀴즈 점수가 50점, 손으로 짠 그룹이 67점이었습니다. 디버깅 문항에서 격차가 가장 컸습니다. 속도 이득은 2분 남짓이었고요. 대응은 AI를 안 쓰는 게 아니라 쓰는 방식을 바꾸는 것입니다. 코드를 받는 데서 멈추지 말고 "왜 이렇게 했는지" 되묻기, 에러를 스스로 한 번 만나보기, 학습·설명 모드 쓰기. 오늘 실습에서 AI 없이 변경 내용을 60초 안에 설명하기를 완료 기준에 넣은 이유입니다.

Q3. 우리 내부망 모델은 GPT/Claude보다 약한데 의미가 있나요?

세 가지로 답합니다. ①Agent = Model + Harness입니다. LangChain은 모델을 안 바꾸고 하네스만 고쳐 Terminal-Bench 30위→5위로 갔습니다. ②오픈웨이트 격차가 빠르게 좁혀지고 있습니다. ③그리고 외부 모델은 애초에 우리 코드를 볼 수 없습니다. 볼 수 없는 최고 성능보다 볼 수 있는 충분한 성능이 낫습니다.

Q4. 벤치마크 1등 모델로 바꾸면 안 되나요?

리더보드 숫자는 모델만의 점수가 아니라 모델+하네스+채점방식의 합산입니다. 같은 모델이 어디서 재느냐에 따라 10점 넘게 흔들립니다. 실제로 이번에 조사해보니 같은 벤치마크 상위값이 출처별로 76%~96%까지 벌어졌습니다. 봐야 할 건 순위가 아니라 우리 코드베이스에서의 재현 가능한 성공률입니다.

Q5. 멀티에이전트는 항상 좋은가요?

아닙니다. 토큰·지연이 에이전트 수만큼 곱해지고, 중복 조사, 지시 유실, 파일 충돌, 권한과 공격면 확대가 따라옵니다. 특히 오케스트레이터가 워커 결과를 다 받으면 4개 이상에서 컨텍스트가 자주 넘칩니다. 단일 에이전트보다 측정 가능한 이점이 있을 때만 켭니다.

Q6. 같은 파일을 여러 에이전트가 동시에 고치면요?

git worktree add ../feat-a -b feat-a — 같은 저장소의 별도 작업 디렉터리를 하나씩 줍니다. 담당 범위를 나누거나 브랜치/worktree로 격리하고, 하나의 작업을 여러 에이전트가 동시에 쓰게 두지 않습니다.

Q7. 지식화하면 모델이 학습되나요?

아닙니다. 가중치는 안 바뀝니다. 문서를 파싱해 검색 가능한 형태로 저장했다가 필요할 때 대화 맥락에 넣는 것입니다. 파인튜닝과는 완전히 다릅니다.

Q8. RAG/벡터DB는 안 쓰나요?

코드 검색에서는 업계가 이미 방향을 틀었습니다. Claude Code는 2025년 5월에 벡터 검색을 걷어내고 grep으로 갔고, 결과가 훨씬 좋았습니다. 인덱스 동기화도 없고 항상 현재 파일 상태를 봅니다. 다만 문서·가이드는 여전히 검색형 지식이 맞습니다. 코드는 grep, 문서는 지식화 — 이렇게 나눕니다.

Q9. MCP 서버 추가하면 바로 안전한가요?

아닙니다. 로컬 MCP 서버는 설치 프로그램처럼 취급해야 합니다. 출처·owner·권한·데이터·토큰·도구 범위·로그·프롬프트 인젝션 가능성을 봐야 합니다. 참고로 MCP 스펙은 어제(7/28) 크게 개정됐습니다. 세션이 프로토콜에서 빠지고 스테이트리스가 됐어요. MCP 얘기는 반드시 버전을 붙여서 하셔야 합니다.

Q10. readOnlyHint 있으면 읽기 전용 아닌가요?

스펙상 annotation은 힌트이지 보안 통제가 아닙니다. 신뢰한 서버와 실제 인가가 있어야 합니다.

Q11. 프롬프트 인젝션이 코딩에서도 생기나요?

생깁니다. 저장소 README, 이슈, 의존성 문서, MCP 도구 설명, 검색 결과가 모델에 행동을 지시할 수 있습니다. 근본 원인은 LLM이 명령과 데이터를 구조적으로 구분할 수 없다는 겁니다. 그래서 lethal trifecta — 비공개 데이터 + 신뢰 못할 텍스트 + 유출 경로 — 셋 중 하나는 끊어야 합니다.

Q12. AI가 알려준 패키지 설치해도 되나요?

확인 전엔 안 됩니다. 오픈소스 모델은 평균 21.7%, 상용 모델도 5.2%가 없는 패키지를 지어냅니다. 더 무서운 건 재현성입니다 — 같은 프롬프트 10번에 환각 이름의 43%가 매번 똑같이 나옵니다. 공격자가 그 이름을 미리 등록해둡니다. 존재·레지스트리·owner·버전·라이선스·취약점을 확인하고 설치하세요.

Q13. 생산성이 정말 오르나요? 반대 연구도 있던데요.

둘 다 맞습니다. 산출량은 대체로 늘어납니다. 동시에 METR 실험에서는 숙련 개발자가 익숙한 저장소에서 오히려 19% 느려졌고, 본인들은 빨라졌다고 느꼈습니다. DORA 2026은 AI를 증폭기라고 부릅니다 — 개인 효과성도 올리고 전달 불안정성도 올립니다. 그래서 도입은 도구 배포가 아니라 검증 체계 설계입니다.

Q14. 코드 품질이 떨어진다던데요?

그 신호는 실재합니다. 리팩터링 비중이 줄고 기술부채가 늘었다는 대규모 분석이 있습니다. 다만 원인은 AI가 아니라 "검증 없는 속도" 입니다. 그래서 PR 크기 상한, 테스트 필수, PR 리뷰 게이트, 린터로 아키텍처 강제 — 이런 하네스가 같이 가야 합니다. OpenAI가 100만 줄을 만들 때 한 일이 정확히 그것이었습니다.

Q15. 우리 코드가 외부로 나가나요?

택가이코드는 내부망 온프렘 구성입니다. 다만 정확한 로그 저장 범위·보존기간은 제품/보안 담당 기준으로 답변드리겠습니다. (※ 강사 주: 이 항목은 절대 추측 금지. 사전에 실제 정책 확인 필수)

Q16. 도구가 37개인가요 50개 이상인가요?

제품 버전에 따라 inventory가 다릅니다. 교육에 배포한 빌드에서 직접 목록을 출력해 기준일과 함께 말씀드리겠습니다.

Q17. Cursor/Claude Code 대비 어떤가요?

표면과 관리체계가 다릅니다. 비교는 브랜드가 아니라 ①어디서 실행되고 ②무엇을 볼 수 있고 ③무엇을 실행할 권한이 있고 ④누가 감사할 수 있는가 로 하셔야 합니다. 4번이 금융권에서는 결정적입니다.

Q18. Skill과 MCP 차이는?

Skill은 반복 가능한 작업 절차이고, MCP는 외부 데이터·도구를 연결하는 프로토콜입니다. 스킬은 "어떻게 하는지", MCP는 "무엇에 닿는지"입니다.

Q19. 앞으로 뭐가 더 옵니까?

세 방향입니다. ①과업 시간축의 연장 — 분에서 시간, 시간에서 일로. METR 측정에서 4~7개월마다 2배입니다. ②감독의 지능화 — 에이전트가 스스로 "이건 사람에게 물어야 한다"를 판단. ③개발자 밖으로 확장 — 데스크톱·비개발 직군. 저희 데스크톱 로드맵이 3번입니다.

Q20. 오늘부터 뭘 하면 되나요?

세 개만 하세요. ① 저장소에 AGENTS.md(또는 .techai.md)를 100줄 이내 목차로 만들기. ② 작은 diff + 테스트를 기본 리듬으로. ③ 에이전트가 같은 실수를 하면 프롬프트를 고치지 말고 환경(린터·테스트·규칙)을 고치기. 세 번째가 하네스 엔지니어링의 전부입니다.

3. 모델과 LLM: 강사가 설명할 최소 깊이

3.1 안정적으로 알아야 할 개념

  • foundation model: 다양한 하위 업무에 적응하는 범용 사전학습 모델
  • LLM: 언어와 코드의 token sequence를 다루는 대규모 모델
  • multimodal model: 텍스트 외 이미지, 음성, 영상, UI 상태 등을 함께 다루는 모델
  • token: 모델이 처리하는 기본 단위. 문자나 단어와 정확히 일치하지 않는다.
  • embedding: 텍스트·이미지 등을 의미 공간의 vector로 표현한 값
  • Transformer: attention으로 sequence 안의 관계를 계산하는 기본 구조
  • pretraining: 대규모 데이터에서 일반 패턴을 학습
  • post-training: instruction following, preference, safety, tool use를 강화
  • inference: 학습된 weight로 실제 응답을 생성하는 과정
  • reasoning effort/test-time compute: 한 요청에 더 많은 탐색·계산을 투입하는 운영 설정
  • MoE: 일부 expert만 선택적으로 활성화해 계산 효율을 얻는 구조
  • distillation: 큰 모델의 행동을 작은 모델에 전달
  • quantization: weight 표현 정밀도를 낮춰 메모리·속도 비용을 줄임
  • fine-tuning/LoRA: 특정 업무나 행동 양식을 weight에 반영
  • RAG: 외부 지식을 검색해 현재 요청의 근거로 제공

3.2 2026 모델 트렌드

  1. 하나의 “최고 모델”보다 작업·가격·속도에 따른 family와 routing이 일반화됐다.
  2. reasoning은 고정된 별도 모델 종류가 아니라 effort, budget, tool loop와 함께 운영된다.
  3. coding, browser, computer use, document work가 모델 발표의 핵심 평가 축이 됐다.
  4. 긴 컨텍스트와 prompt cache가 확대됐지만 relevant context를 고르는 문제는 사라지지 않았다.
  5. open-weight 모델의 비용·배포 선택지가 넓어졌지만 라이선스와 완전한 재현 가능성은 별개다.
  6. 모델 발표 점수보다 독립 평가, harness recipe, 비용, latency, 거부율, 안전성을 함께 봐야 한다.

현재 모델에 대한 가장 안전한 설명:

3.4 open source라는 말의 정확한 구분

  • open source AI: OSI Open Source AI Definition이 요구하는 수정·재현·사용에 필요한 구성요소와 권리가 충족되는 범주
  • open model: 공개 접근 모델이라는 느슨한 표현
  • open weights: weight 파일을 받을 수 있다는 뜻
  • source-available: 일부 source나 weight는 공개하되 사용 제약이 존재

따라서 “weight를 받을 수 있다 = open source”는 틀린 설명이다. 라이선스, 학습 정보, 코드, 데이터 정보, 수정·재배포 권리를 따로 확인한다.

4. 에이전트와 workflow

4.1 operational definition

workflow는 사람이 미리 정한 경로를 실행한다. agent는 목표와 제약 안에서 모델이 다음 도구, 순서, 분기, 재시도, 중단 중 일부를 동적으로 결정한다.

에이전트를 단순히 “LLM이 여러 번 대답하는 것”으로 가르치면 안 된다. 상태, 도구, 부작용, 권한, 종료조건이 있어야 시스템 관점의 에이전트를 설명할 수 있다.

4.2 workflow가 더 나은 경우

  • 경로와 규칙이 이미 알려져 있음
  • 규정·감사·재현성이 중요함
  • 실패 비용이 큼
  • 입력·출력 schema가 안정적임
  • 예외를 코드로 처리할 수 있음

4.3 agent가 유리할 수 있는 경우

  • 저장소나 자료를 먼저 탐색해야 함
  • 문제 분해와 도구 선택이 업무의 핵심임
  • 정해진 경로가 없고 피드백을 보며 수정해야 함
  • 사람이 모든 분기를 작성하는 비용이 큼
  • 중간 상태를 관찰해 복구할 수 있음

5. 멀티에이전트

5.1 언제 쓸 것인가

  • 서로 독립적인 자료를 병렬 조사
  • 보안, 품질, 요구사항처럼 다른 관점의 review
  • 서로 다른 권한·도메인을 격리
  • 긴 작업의 context를 역할별로 분리
  • 동일 답을 복제하는 것이 아니라 서로 다른 증거를 생산

5.2 언제 쓰지 말 것인가

  • 한 agent가 짧게 끝낼 수 있음
  • 같은 파일을 동시에 수정해야 함
  • 작업 경계와 통합 owner가 없음
  • 결과를 검증할 수 없음
  • token·latency·운영 복잡성이 이익보다 큼
  • 동일 모델·동일 prompt의 다수결만 수행

5.3 topology

  • manager-workers: manager가 작업을 분해하고 합성
  • peer-to-peer: agent끼리 메시지와 artifact 교환
  • blackboard: 공용 상태에 결과를 기록
  • pipeline: specialist가 순서대로 인계
  • debate/critic: 생성자와 비평자 분리
  • map-reduce: 병렬 탐색 후 중앙 합성
  • hierarchical: 여러 manager와 worker 계층

5.4 운영 규칙

  1. 한 task에는 한 owner를 둔다.
  2. 쓰기 workspace는 worktree, branch, container로 격리한다.
  3. DAG와 dependency를 명시한다.
  4. parent가 통합, 충돌, 최종 검증을 소유한다.
  5. time, token, turn, recursion, concurrency budget을 둔다.
  6. 하위 agent 결과를 비신뢰 입력으로 취급한다.
  7. agent가 멈춘 것을 완료로 보지 말고 acceptance evidence를 확인한다.

6. Prompt, context, RAG, memory, skill

6.1 범위 차이

  • prompt engineering: 요청과 지시를 쓰는 기술
  • context engineering: 목표 달성에 필요한 정보와 상태를 선택·배치·갱신하는 기술
  • harness engineering: context를 포함해 실행 루프, 도구, 환경, 권한, 검증, 관측을 설계하는 기술
  • platform engineering: 여러 팀이 안전하게 사용할 공통 실행·배포·개발 기반

6.2 긴 context가 RAG를 대체하지 않는 이유

기법해결하는 문제
Long context한 요청이 볼 수 있는 최대 범위
RAG필요한 자료를 찾고 근거로 제공
Memory세션을 넘어 선택된 상태를 유지
Prompt cache/KV cache반복 입력의 계산 비용과 latency 절감
Compaction오래된 실행 상태를 압축해 다음 context로 전달

긴 context도 relevance, freshness, 권한 filtering, 출처, lost-in-the-middle, context rot 문제를 해결하지 않는다. 실무에서는 hybrid가 일반적이다.

6.3 RAG pipeline

RAG 품질은 “답이 좋아 보인다”로 평가하지 않는다.

  • 검색: recall@k, precision@k, MRR, nDCG, 권한 위반 0
  • 답변: citation correctness, groundedness, completeness, abstention
  • 운영: freshness, latency, cost, 삭제 반영 시간, owner coverage

6.4 memory lifecycle

  • working memory: 현재 실행의 임시 상태
  • episodic memory: 과거 작업과 사건
  • semantic memory: 일반화된 사실
  • procedural memory: 반복 절차
  • environment state: 파일, branch, issue, 실행 결과
  • experience memory: 성공·실패에서 추출한 교훈

전체 chat를 영구 저장하는 것은 memory design이 아니다. 저장할 항목을 선택하고, source·version·owner·expiry·delete policy를 붙이며, 사용자와 업무 권한을 보존해야 한다.

6.5 knowledge, memory, skill, rule

  • knowledge: 현재 업무가 참조할 사실
  • memory: 여러 실행 사이에 지속되는 선택된 상태
  • skill: 반복 가능한 절차와 필요한 artifact
  • rule: 허용·금지·승인·품질 기준
  • tool: 환경에서 실제 행동을 수행하는 capability

Agent Skills의 SKILL.md는 절차를 progressive disclosure 방식으로 제공할 수 있지만, allowed-tools 같은 필드도 제품별 지원과 실제 권한 강제를 따로 확인해야 한다.

8. 하네스 엔지니어링

8.1 정확한 정의

Agent harness는 foundation model을 제외하고, agent가 무엇을 관찰하고 기억하며 호출하고 수정할 수 있는지, 어떤 피드백을 받고 무엇을 증명해야 완료되는지를 중재하는 runtime/control system이다.

Harness engineering은 그 runtime과 control을 설계, versioning, 운영, 측정, 개선하는 지속적 engineering discipline이다.

“하네스 엔지니어링”이라는 표현의 최초 창안자를 단정할 근거는 없다. OpenAI와 Anthropic의 2025~2026 engineering 사례가 개념을 구체화했으며, 더 넓게는 agent runtime, scaffolding, evaluation harness, platform engineering의 연속선에 있다.

8.2 하네스의 12개 구성요소

  1. mission contract: 목표, scope, acceptance, stop/escalation
  2. instruction hierarchy: system, organization, repository, task rule
  3. context builder: relevant code, docs, errors, state, provenance
  4. state/memory: durable progress, checkpoint, compaction, handoff
  5. typed tools: schema, side-effect class, timeout, cancellation, errors
  6. environment: worktree, container, terminal, browser, network
  7. identity/permission: scoped credential, allow/ask/deny, approval
  8. orchestration: planning, routing, subagent, concurrency, retry
  9. verification: lint, typecheck, test, build, security, runtime QA
  10. observability: prompt/tool/model/version/trace/cost/outcome
  11. human control: preview, diff, approval, override, kill switch
  12. feedback loop: recurring error를 rule, skill, lint, test, eval로 승격

8.3 reference architecture

8.4 주요 contract

Tool contract

  • typed input/output
  • side-effect: read/write/execute/network/admin
  • idempotency와 retry 안전성
  • timeout/cancel
  • stable error taxonomy
  • credential scope
  • tool result는 untrusted data
  • secret 없는 audit event

Context contract

  • repository-local, versioned source of truth
  • 짧은 entry point와 progressive disclosure
  • source, owner, date, validity
  • compaction 후에도 intent와 acceptance 보존
  • chat 밖 durable state

Multi-agent contract

  • owner와 writable scope
  • worktree/branch isolation
  • dependency DAG
  • bounded concurrency
  • parent의 integration 책임

Completion contract

  • agent가 “완료”라고 말한 것은 증거가 아님
  • evidence가 acceptance item과 1:1로 연결
  • test를 통과해도 runtime, security, maintainability를 별도 판단

8.5 OpenAI 사례를 과장하지 않는 법

OpenAI의 harness engineering 사례는 repository knowledge, worktree별 실행환경, UI·log·metric 가시성, 구조적 lint, agent review, 지속적인 “garbage collection”의 가치를 잘 보여준다. 그러나 특정 greenfield 내부 제품의 “10배 빠름”을 일반 생산성 법칙으로 옮기면 안 된다. 같은 수준의 repository legibility, CI, observability, sandbox, feedback loop 투자가 있어야 한다.

18. 강사가 받아야 할 어려운 질문

모델

Q. reasoning model은 일반 LLM과 다른가? A. 같은 foundation family에 reasoning post-training과 더 큰 test-time compute를 적용하는 경우가 많다. 제품명이 아니라 effort, latency, token, tool loop를 함께 봐야 한다.

Q. chain of thought를 보여주면 믿을 수 있나? A. reasoning summary는 유용한 설명일 수 있지만 실제 내부 원인의 충실한 기록이라고 보장할 수 없다. 결과와 외부 증거를 검증한다.

Q. context가 1M이면 RAG가 필요 없나? A. 아니다. 필요한 source 선택, freshness, ACL, citation, retrieval cost 문제는 남는다.

Q. open source 모델이 사내에 더 안전한가? A. data egress를 줄일 수 있지만 운영 취약점, supply chain, patch, access control, logging 책임이 사내로 이동한다. 라이선스도 별도다.

Agent

Q. agent와 workflow의 차이는? A. 다음 행동과 분기를 모델이 동적으로 고르는 정도다. 안정된 경로는 workflow가 더 싸고 예측 가능하다.

Q. agent가 알아서 끝까지 하면 왜 사람이 필요한가? A. 목표·가치·권한·예외·책임은 자동으로 결정되지 않는다. 사람은 specification, risk, acceptance, override를 소유한다.

Q. 여러 agent면 더 정확한가? A. 독립 증거와 역할 분리가 있을 때 가능하다. 같은 모델·prompt를 복제하면 상관 오류와 비용만 늘 수 있다.

Q. subagent와 A2A agent는 같은가? A. subagent는 한 runtime 내부 delegation일 수 있다. A2A는 독립·opaque agent application 사이의 protocol이다.

Context와 지식

Q. 문서를 지식화하면 모델이 학습되나? A. 보통 weight training이 아니라 parsing, indexing, retrieval, context injection이다.

Q. memory를 많이 저장할수록 좋은가? A. stale, poisoned, private memory가 누적될 수 있다. 선택, source, expiry, deletion이 필요하다.

Q. citation이 있으면 정확한가? A. citation이 실제 주장을 support하는지, source가 최신·권위 있는지 확인해야 한다.

MCP와 protocol

Q. MCP는 REST API를 대체하나? A. 아니다. agent가 tool/data capability를 발견·호출하는 공통 interface이며 실제 backend가 REST일 수 있다.

Q. MCP server를 붙이면 안전한가? A. 아니다. 설치와 연결은 trust가 아니다. owner, code, scope, credential, data, log, rollback을 검토한다.

Q. A2A와 MCP 중 무엇을 선택하나? A. tool/data capability면 MCP, 독립 agent와 task/artifact를 주고받으면 A2A다. 함께 쓸 수 있다.

Q. ACP가 MCP를 대체하나? A. ACP는 editor와 coding agent, MCP는 agent와 tool/data server 사이를 표준화한다.

Coding과 평가

Q. 어떤 code assistant가 최고인가? A. task, repository, language, data boundary, execution surface, policy, budget에 따라 다르다. 같은 private eval로 비교한다.

Q. SWE-bench 점수로 고르면 안 되나? A. task defect, contamination, harness 차이가 크고 Verified와 Pro 모두 신뢰 문제가 확인됐다. portfolio와 private eval이 필요하다.

Q. test를 통과했으면 끝인가? A. test coverage 밖의 오류, security, maintainability, UI behavior가 남는다. runtime QA와 review가 필요하다.

Q. AI code가 많아지면 생산성이 오른 것 아닌가? A. output volume은 가치가 아니다. accepted change, review time, defect, lead time, incident, 사용자 결과를 측정한다.

보안과 조직

Q. system prompt로 injection을 막을 수 있나? A. 단독으로는 안 된다. untrusted data 분리, least privilege, sandbox, approval, egress control이 필요하다.

Q. allow/ask/deny면 충분한가? A. ask는 안전 판단이 아니라 승인 요청이다. 승인 피로, tool 조합, autopilot, background execution을 고려해야 한다.

Q. ZDR이면 data가 아무 데도 안 남나? A. 적용 product, model provider, client, trace, MCP, local log, 예외 feature를 확인해야 한다. 하나의 ZDR 문구를 전체 system에 전이하면 안 된다.

Q. AI가 만든 결과의 책임은 누구에게 있나? A. 배포·업무 판단을 승인한 조직과 사람이 책임 구조를 가져야 한다. agent에게 책임을 넘길 수 없다.

2. 핵심 개념

Agent와 workflow

  • workflow: 미리 정한 단계로 실행
  • agent: 모델이 도구·순서·분기·중단 중 일부를 동적으로 결정
  • 규정 준수와 예측 가능성이 중요하면 workflow가 적합
  • 탐색·분해·도구 선택이 중요하면 agent가 유리할 수 있음

Context engineering

큰 context가 좋은 context는 아니다.

좋은 context에는 다음이 들어간다.

  • 목표와 완료 기준
  • 관련 파일·오류·문서
  • 현재 상태
  • 적용할 규칙과 제한
  • 이미 실패한 시도
  • 검증 방법
  • 출처와 버전

관련 없는 전체 저장소·오래된 대화·중복 문서는 attention을 분산시킨다.

Knowledge, memory, skill, rule

  • knowledge: 현재 과업에 검색·참조할 사실
  • memory: 여러 과업 사이에 지속되는 정보
  • skill: 반복 가능한 작업 절차
  • rule: 허용·금지·승인 같은 행동 제약

보안 경계는 문장으로만 적지 않는다. 샌드박스·권한·네트워크 정책·자격증명 격리처럼 실행환경에서 강제해야 한다.

MCP

  • host: 사용자·모델·정책을 조정하는 애플리케이션
  • client: host가 한 MCP server와 유지하는 연결
  • server: resource, prompt, tool 등을 제공
  • stdio: 로컬 프로세스 방식
  • Streamable HTTP: 원격/독립 서비스 방식

2026-07-28 MCP 사양은 이전 버전과 비교해 세션·초기화·authorization 세부가 달라졌다. 구현 세부는 반드시 버전을 붙여 말한다. MCP 2026-07-28 specification↗, key changes↗

안전수칙:

  • 로컬 MCP 서버는 설치 프로그램처럼 취급
  • 신뢰한 서버만 allowlist
  • tool 이름·설명·annotation만 보고 안전하다고 판단하지 않음
  • 자격증명을 prompt/context/log에 넣지 않음
  • 원격 token은 audience와 scope를 제한
  • 쓰기·삭제·전송·관리 작업은 별도 승인
  • read와 write 도구를 가능한 한 분리

Multi-agent

장점:

  • 독립적인 탐색을 병렬화
  • 다른 관점으로 리뷰
  • 도메인별 전문화
  • 작업 격리

비용:

  • token·latency 증가
  • 같은 조사를 중복
  • 지시와 완료 기준 손실
  • 같은 파일 충돌
  • 더 큰 권한·공격면

따라서 “여러 개가 더 좋다”가 아니라, 한 agent나 workflow보다 측정 가능한 이점이 있을 때만 사용한다.

AI 코딩 생산성

안전한 설명:

AI의 효과는 과업 구조, 경험, 저장소 맥락, 사용 방식, 측정지표에 따라 달라진다. 결과물 수가 늘어도 독립 이해와 디버깅 능력이 같이 늘었다는 뜻은 아니다.

근거:

  • METR 연구의 숙련 오픈소스 개발자는 특정 고맥락 과업에서 AI 사용 시 19% 느렸다.
  • Microsoft·Accenture·Fortune 100의 무작위 현장실험은 pull request 중심 업무출력이 평균적으로 증가했다고 보고했다.
  • 2026년 Anthropic 연구는 낯선 Python 라이브러리 학습에서 AI 사용 집단의 즉시 이해·디버깅 점수가 낮았다고 보고했다.

따라서 수업에서는 결과 코드만 보지 않고 설명, diff, 테스트, 독립 디버깅을 본다.

3. 5분 안전 브리핑 초안

오늘 실습에서는 제공된 샘플 코드와 문서만 사용합니다. 실제 고객정보, 개인정보, 운영계 데이터, 비밀키, 비밀번호, 토큰, 운영 URL은 입력하지 않습니다. AI의 답변과 도구 설명은 참고정보입니다. 파일 수정, Shell, Git, MCP, 외부 전송은 서로 위험도가 다르며, 권한을 요청한다고 해서 그 행동이 안전하다는 뜻은 아닙니다. 실행 전에는 대상 파일과 명령을 읽고, 실행 후에는 diff와 테스트 결과를 확인합니다. 동작하는 코드도 보안·유지보수·라이선스 문제가 있을 수 있습니다. MCP 서버와 Skill은 연결했다는 이유만으로 신뢰하지 않습니다. 출처와 담당자, 필요한 데이터, 읽기·쓰기 범위, 자격증명, 로그를 확인합니다. AI는 금융업무 판단의 보조수단입니다. 최종 판단과 책임은 사람에게 있습니다. 이상한 권한 요청, 고객정보 노출, 의심스러운 dependency, 외부 전송이 보이면 실행하지 말고 helper에게 알려주세요.

금융위원회의 2026 금융분야 AI 7대 원칙은 거버넌스, 합법성, 보조수단성, 신뢰성, 금융안정성, 신의성실, 보안성을 제시하고 최종 의사결정과 책임을 임직원이 수행하도록 한다. 금융위원회↗

4. 예상 Q&A

도구와 동작

Q. ChatGPT, Claude, Codex, Cursor, 택가이코드의 차이는? A. 일반 대화 UI, 코드 편집기, 터미널 coding agent, 사내 관리·권한·로그 체계가 각각 다르다. 브랜드보다 실행 위치, 보는 데이터, 사용할 도구, 승인 방식, 검증 절차로 비교한다.

Q. 에이전트는 코드를 자동으로 바꾸나요? A. 도구와 권한 설정에 따라 가능하다. 읽기·제안·쓰기·실행을 분리하고, 쓰기 뒤에는 diff와 테스트를 확인해야 한다.

Q. Terminal과 VS Code 중 무엇을 쓰나요? A. 프로젝트 루트·Shell·Git 중심이면 Terminal이 직관적이고, 파일·진단·diff를 눈으로 보며 작업하면 VS Code가 편하다. 같은 엔진이라는 내부 설명의 정확한 범위는 제품 담당자에게 확인한다.

Q. 모델이 틀리면 어떻게 하나요? A. 재현 가능한 기대값을 적고, 관련 파일과 근거를 찾고, 작은 가설 하나를 테스트한다. 같은 모델의 자기확신보다 테스트·빌드·로그·동료 리뷰가 강한 증거다.

Skills·Knowledge·MCP

Q. Skill과 MCP의 차이는? A. Skill은 반복 작업 절차이고, MCP는 외부 데이터·도구 시스템을 연결하는 프로토콜이다.

Q. 지식화하면 모델이 학습되나요? A. 보통 모델 가중치를 다시 학습한다기보다 문서를 파싱·검색해 현재 대화 context에 넣는다. 저장·색인·갱신·삭제 방식은 제품 구현을 확인해야 한다.

Q. MCP 서버를 추가하면 바로 안전하게 쓸 수 있나요? A. 아니다. 서버 출처, owner, 권한, 데이터, token, tool 범위, 로그, prompt injection 가능성을 검토해야 한다.

Q. readOnlyHint가 있으면 읽기 전용인가요? A. MCP specification에서 annotation은 힌트이지 보안 통제가 아니다. 신뢰한 서버와 실제 authorization이 필요하다.

Q. 문서가 오래됐거나 서로 충돌하면? A. 출처·작성일·버전을 같이 보여주고, 충돌을 숨기지 않는다. 최신 owner 문서를 우선하되 업무 규정의 권위 체계를 따른다.

멀티에이전트

Q. 여러 agent를 쓰면 무조건 더 좋은가요? A. 아니다. 독립적인 탐색·비교·리뷰에는 유리하지만 비용·지연·중복·충돌이 늘어난다. 한 agent로 충분한 일은 single이 낫다.

Q. 같은 파일을 동시에 바꾸면? A. 담당 범위를 나누거나 별도 branch/worktree를 사용한다. 하나의 작업을 여러 agent가 동시에 쓰게 두지 않는다.

보안과 금융권 사용

Q. 운영 코드나 고객정보를 넣어도 되나요? A. 내부 정책에서 명시적으로 승인한 범위가 아니라면 안 된다. 수업에서는 정제된 샘플만 사용한다.

Q. API Key는 어디에 넣나요? A. 승인된 비밀 저장소·환경변수·제품 설정을 사용하고, prompt·source file·screenshot·채팅·로그에 붙이지 않는다.

Q. 로그에는 무엇이 남나요? A. 택가이Web/Code의 현재 구현과 내부 보존정책을 확인해 답해야 한다. 질문, 응답, 도구 인자·결과, 오류, 파일명, 사용자정보 각각을 구분한다.

Q. AI가 만든 dependency를 설치해도 되나요? A. 패키지 존재, 공식 registry, owner, version, license, 취약점과 유지상태를 확인하기 전에는 설치하지 않는다.

Q. prompt injection은 코딩에서도 생기나요? A. 생긴다. 저장소 문서, 이슈, dependency, MCP tool 설명이나 검색 결과가 모델에 행동을 지시할 수 있다. 외부 텍스트를 명령으로 신뢰하지 않는다.

수치와 제품상태

Q. 87.5% 단축은 어떻게 계산했나요? A. 수업 전에 대상 화면 수, 기존/AI 방식 MM, 포함·제외 작업, 측정자, 최대값/평균 여부를 준비한다. 근거가 없으면 “단일 내부 POC에서 관찰한 최대값” 이상으로 일반화하지 않는다.

Q. 17억~90억은 확정 절감인가요? A. 슬라이드상 추정치다. 감사·결재 확정 절감과 같은 수준으로 말하지 않는다.

Q. 37개인가요, 50개 이상인가요? A. 제품 버전이 다르면 inventory가 달라질 수 있다. 교육에 배포할 빌드에서 직접 도구 목록을 출력해 기준일과 함께 답한다.

Q. ChatGPT 앱이 Codex로 개명됐나요? A. 반대 방향에 가까운 한정된 전환이다. 이전 Codex desktop app이 새 ChatGPT desktop app으로 이동했고, 그 안에 Codex가 별도 view로 남는다. Codex 전체가 ChatGPT로 개명된 것은 아니다. OpenAI migration notice↗

Q. “가장 많이 쓰는” 도구인가요? A. 현재 자료에는 비교 가능한 시장점유율 근거가 없다. “대표적인 예”라고 말하는 것이 안전하다.

2. 인력과 좌석 운영

40명이 동시에 코딩 에이전트를 사용하면 강사가 설명과 개별 장애 대응을 같이 맡을 수 없다. The Carpentries는 일반적인 워크숍 팀을 host, 2명 이상의 instructor, helpers로 구분하고, 한 명이 설명할 때 다른 사람이 교실을 돌며 돕는 “teach and assist” 방식을 안내한다. 고정된 보조자 비율을 제시하지는 않는다. The Carpentries: Working With Your Team↗

이 과정에서는 다음 구성을 운영 목표로 둔다. 이는 보편 법칙이 아니라 40명·사내 계정·AI 도구 실습이라는 조건에 맞춘 운영 판단이다.

  • 강사 1명: 설명, 라이브 데모, 전체 속도 결정
  • 공동 진행 또는 수석 helper 1명: 공통 장애 판단, 강사에게 중단 신호
  • helper 2명: 설치·계정·권한·실습 오류 순회 지원
  • 별도 host 1명: 출석, 좌석, 마이크, 시설, 공지 담당

총 5명은 이 과정의 최소 운영 목표다. 사전 설치 완료율이 낮거나 참가자 기기·숙련도·접근성 요구가 다양하면 helper를 더 확보해 6~8명 체제로 운영하는 편이 안전하다. 실제 필요 인원은 T-7 리허설의 도움 요청 건수와 대기시간으로 확정한다.

학습자는 4명씩 10개 조로 앉힌다. helper 3명이 각각 3~4개 조를 맡고, 조 안에서는 다음 역할을 15분마다 교대한다.

  • Driver: 직접 키보드를 조작
  • Navigator: 요구사항과 다음 단계 확인
  • Reviewer: diff·테스트·위험 확인
  • Recorder: 오류와 해결방법 기록

도움 요청은 손들기 대신 파란색/노란색 카드나 온라인 대기열을 쓴다.

  • 파란색: 완료, 다음 단계 가능
  • 노란색: 도움이 필요하지만 계속 작업 중
  • 노란색 요청이 8개 이상 쌓이면 강사가 전체 진행을 멈추고 공통 원인을 설명

색각 다양성을 위해 빨강·초록 조합은 피한다. 이 방식은 도움 요청을 눈에 보이게 하고 학습자가 기다리는 동안 계속 작업할 수 있게 한다. The Carpentries: Working With Your Team↗

  • 요구사항과 기존 동작을 먼저 적음
  • 관련 컴포넌트·상태·테스트를 찾음
  • 작은 diff
  • 실행 또는 테스트 증거
  • 변경을 60초 안에 설명
