1

기본기 — LLM이라는 엔진

모든 용어의 출발점. 여기 6개만 잡으면 나머지 장이 전부 쉬워집니다.

LLM

Large Language Model☕

다음에 올 말을 확률로 예측하도록 거대한 텍스트로 학습된 모델. 코드도 "말"이라서 코딩을 합니다.

☕ 쉽게 말하면 — 세상의 글을 엄청나게 읽고 "다음 단어 맞히기"의 신이 된 존재. 정답을 아는 게 아니라 가장 그럴듯한 걸 말합니다. 이 한 줄이 환각(4번째 용어)의 복선입니다.

토큰 · 컨텍스트 윈도우

token · context window☕

토큰 = 모델이 글을 세는 단위(한글 1자 ≈ 1~2토큰). 컨텍스트 윈도우 = 모델이 한 번에 볼 수 있는 토큰 한도.

☕ 쉽게 말하면 — 컨텍스트 윈도우는 책상 크기입니다. 책상이 아무리 커도, 서류를 산처럼 쌓으면 정작 필요한 종이를 못 찾죠. 그게 다음 용어입니다.
❌ 흔한 오해 — "1M 토큰 모델이니까 1M을 다 넣으면 되지."
✅ 사실 — 광고 창(1M)과 실효 컨텍스트(정확도가 유지되는 구간, 대략 200~400K)는 다릅니다. 200K 모델이 5만 토큰에서 이미 정확도를 잃는 연구도 있습니다(Chroma, 18개 모델).

추론 모델 · 생각 토큰

reasoning model · thinking budget☕

답하기 전에 "생각 토큰"을 태우며 문제를 풀어보는 모델. 수학·코드·계획에 강하지만 느리고 비쌉니다. 생각의 양을 조절하는 손잡이가 thinking budget(effort).

☕ 쉽게 말하면 — 일반 모델은 즉답하는 사람, 추론 모델은 연습장에 풀어보고 답하는 사람. 연습장 쓰는 시간만큼 느리고, 연습장 종이값(토큰)이 듭니다.

환각 · 그라운딩

hallucination · grounding☕

환각 = 근거 없는 내용을 그럴듯하게 생성하는 것. 그라운딩 = 답을 실제 근거(문서·코드·검색결과)에 묶는 것.

☕ 쉽게 말하면 — LLM은 "모른다"보다 "그럴듯한 오답"을 잘 만듭니다. 그래서 5장(RAG·검색)과 3장(하네스의 검증 루프)이 존재합니다. 이 책 절반은 사실 환각 대책입니다.

오픈웨이트 vs 폐쇄형

open-weight vs closed☕

가중치 파일을 내려받아 내 서버에서 돌릴 수 있으면 오픈웨이트, API로만 쓸 수 있으면 폐쇄형. 오픈웨이트 ≠ 오픈소스(학습 데이터·코드 공개와는 다른 얘기).

☕ 쉽게 말하면 — 온프렘(내부망) 가능 여부가 여기서 갈립니다. 금융권처럼 데이터가 밖으로 못 나가는 곳에서 이 축이 모델 선택의 1번 기준.

파인튜닝 vs RAG vs 지식화

fine-tuning vs RAG☕

파인튜닝 = 가중치 일부를 다시 학습(모델 자체가 변함). RAG·지식화 = 모델은 그대로 두고 필요할 때 자료를 찾아 옆에 놓아주는 것.

❌ 흔한 오해 — "문서를 지식화하면 모델이 학습되나요?"
✅ 사실 — 아니요. 가중치는 1도 안 바뀝니다. 문서를 파싱해 검색 가능한 형태로 저장했다가, 필요할 때 대화 맥락에 넣어주는 겁니다. 파인튜닝과 완전히 다릅니다.
2

코드 어시스턴트 — 에이전트의 탄생

"채팅으로 물어보기"에서 "일을 맡기기"로. 1편(트렌드)에서 본 도구들이 여기 다 들어옵니다.

4가지 표면

surfaces: Web · CLI · IDE · Desktop☕

같은 모델이라도 만나는 창구가 다릅니다. 웹 UI(ChatGPT·Claude 웹) → CLI 에이전트(Claude Code·Codex) → IDE 통합(Cursor 등) → 데스크탑 앱. 모델 회사들은 거의 같은 순서로 이 표면들을 만듭니다.

☕ 쉽게 말하면 — 같은 요리사(모델)가 홀 서빙(웹), 출장 요리(CLI), 주방 상주(IDE)로 일하는 차이. 일을 맡기려면 파일을 읽고 명령을 실행할 수 있는 CLI/IDE 쪽으로 와야 합니다.

에이전트 · 에이전틱 루프

agent · agentic loop☕

에이전트 = 모델이 도구·순서·분기·중단을 스스로 결정하며 목표를 향해 반복 실행하는 시스템. 그 반복이 에이전틱 루프: 계획 → 도구 → 관찰 → 판단 → (반복).

강의에서 그대로 쓰는 문장"모델은 '무엇을 하고 싶다'고 말할 뿐이고, 실제로 할지 말지는 하네스가 결정합니다. 그래서 보안은 모델이 아니라 하네스에 겁니다."

Workflow vs Agent

☕

워크플로는 사람이 단계를 미리 고정, 에이전트는 모델이 단계를 동적으로 결정.

WorkflowAgent
단계사람이 미리 고정모델이 동적으로 결정
예측가능성높음낮음
감사·규제 적합좋음어려움
맞는 일정형·반복·규정준수탐색·분해·낯선 코드베이스
☕ 쉽게 말하면 — 규정이 걸린 곳은 워크플로, 탐색이 필요한 곳은 에이전트. "전부 에이전트로!"는 오답입니다.

AGENTS.md · CLAUDE.md

프로젝트 지침 파일☕

저장소에 두는 "에이전트용 사용설명서". 코딩 규칙, 금지사항, 빌드 방법을 적어두면 에이전트가 매 세션 읽고 시작합니다. AGENTS.md는 크로스툴 표준, CLAUDE.md는 Claude Code용, .techai.md·rules.md는 같은 개념의 변형.

☕ 쉽게 말하면 — 신입사원 첫날 주는 온보딩 문서. 에이전트는 매일 첫날이라서, 이 문서가 좋을수록 매일이 좋아집니다.

바이브 코딩 → 에이전틱 엔지니어링

vibe coding → agentic engineering☕

바이브 코딩 = 결과만 보고 코드는 안 읽으며 "느낌으로" 만들기. 프로토타입엔 좋지만 운영엔 위험. 2026년의 방향은 에이전틱 엔지니어링 — 에이전트에게 맡기되 스펙·검증·리뷰의 공학 규율을 유지하는 것.

☕ 쉽게 말하면 — 바이브 코딩이 "맛만 보고 합격"이라면, 에이전틱 엔지니어링은 위생검사까지 통과시키는 것. 관련 규율: Plan mode(계획만 세우는 읽기전용), TDD with agents(테스트 먼저 주고 통과까지 반복), SDD(스펙 먼저 쓰는 Spec-Driven Development).
3

하네스 — 이 책의 심장

2026년 업계에서 가장 뜨거운 단어. 2편(택가이 코드)의 킬러 슬라이드가 바로 여기 서 있습니다.

하네스

harness — Agent = Model + Harness☕

모델의 추론을 제외한 전부. 도구 실행, 상태 관리, 메모리, 권한, 검증, 재시도, 관측. Terraform을 만든 Mitchell Hashimoto가 "Agent = Model + Harness" 공식으로 정리했고 2026년 초 업계 표준어가 됐습니다.

2026년의 명언"Agents aren't hard; the Harness is hard." — Ryan Lopopolo, OpenAI

층을 나누면: 하네스(좁은 의미) = 루프를 실행하는 계층(Claude Code·Codex CLI), 스캐폴드 = 모델이 보는 세계를 정의하는 층(지침 파일·훅·서브에이전트). 커뮤니티 하네스 번들(oh-my-claudecode, 가재코드, LazyCodex, Ouroboros 등)은 스캐폴드 층의 제품들입니다.

하네스 엔지니어링

harness engineering☕

에이전트가 올바른 절차로 끝까지 일하도록 작업환경·제약조건·피드백 루프를 설계하는 규율. 프롬프트를 다듬는 게 아니라 시스템을 깝니다.

☕ 쉽게 말하면 (운전 비유) — "모델은 운전 실력이고, 하네스는 차선, 가드레일, 속도계, 블랙박스, 그리고 브레이크입니다. 운전 실력이 최고여도 밤에 차선 없는 산길에서는 사고가 납니다."

실증 카드 두 장:

  • LangChain 팀은 모델을 전혀 바꾸지 않고 하네스만 최적화해 Terminal-Bench 30위 → 5위
  • OpenAI 엔지니어 3명이 손으로 코드 한 줄 안 쓰고 약 100만 줄 / PR 1,500건을 완성. 비결은 AGENTS.md를 100줄 목차로 유지, 규칙을 린터로 기계적 강제, 저장소를 단일 진실 원천으로
❌ 흔한 오해 — "좋은 프롬프트를 쓰면 에이전트가 규칙을 지킨다."
✅ 사실 — 프롬프트 지시는 확률적 순종, 린터·게이트는 결정적 강제. "규칙을 지켜라"라고 말하는 것과 규칙 위반 시 PR을 막는 것은 다른 차원입니다. 하네스 엔지니어링은 후자를 설계합니다.

4

멀티에이전트 — 혼자보다 팀, 단 공짜는 아님

2026년 오케스트레이션의 표준 문법. 그리고 반드시 함께 알아야 할 비용.

오케스트레이터 · 서브에이전트 · 에이전트 팀

3단계 진화☕

오케스트레이터 = 과업을 분해해 하위 에이전트에 위임하고 결과를 통합하는 상위 에이전트. 서브에이전트 = 독립 컨텍스트와 도구 집합을 가진 하위 에이전트. 에이전트 팀 = 팀원끼리 직접 통신하고 작업 목록을 공유하는 2026년의 최신 형태. 2026년 업계 합의는 "오케스트레이터 + 격리된 서브에이전트 + 요약만 반환".

4가지 표준 패턴

sequential · concurrent · hierarchical · handoff🌶️
패턴구조언제
Sequential 파이프라인A→B→C 순차 전달단계가 명확할 때 (작성→검토)
Concurrent 병렬동시에 실행 후 취합탐색·검색·비교
Hierarchical 오케스트레이터-워커매니저가 분해→위임→통합큰 과업 분해
Handoff제어권 자체를 넘김도메인 라우팅

여기에 Debate(토론·교차평가)를 더해 5패턴으로 세기도 합니다 — 여러 에이전트가 독립 답을 내고 서로 반박·채점(LLM-as-judge)하게 하는 방식. 단, 심판 모델은 채점 기준이 슬금슬금 변하는 캘리브레이션 드리프트가 있어 주기적 인간 검증이 필수입니다.

멀티는 공짜가 아니다

the cost table☕
이득비용
독립 탐색 병렬화토큰·지연이 에이전트 수만큼 곱셈
다른 관점의 리뷰같은 조사를 중복
도메인 전문화지시·완료기준 유실
작업 격리같은 파일 충돌 · 권한/공격면 증가
강의에서 그대로 쓰는 문장"멀티에이전트는 '많을수록 좋다'가 아닙니다. 하나의 에이전트나 워크플로보다 측정 가능한 이점이 있을 때만 켭니다."

파일 충돌의 정답 한 줄: git worktree add — 같은 저장소의 별도 작업 디렉터리를 파서 에이전트마다 격리된 사본에서 일하게 하는 것.

MCP · A2A

연결 규격들🌶️

MCP(Model Context Protocol) = 에이전트 ↔ 도구/데이터를 연결하는 표준 규격(host/client/server, tools/resources/prompts). A2A = 에이전트 ↔ 에이전트 통신 규격(Linux Foundation).

☕ 쉽게 말하면 — MCP는 USB-C 포트입니다. 도구마다 전용 케이블을 만들지 않고, 규격에 맞춰 꽂으면 어떤 에이전트든 그 도구를 씁니다. 단, 아무 USB나 꽂으면 안 되듯 MCP 도구 설명에 명령을 심는 공격(tool poisoning)도 존재 — 신뢰할 수 있는 서버만.
5

RAG와 검색 — 그리고 대전환

대부분의 청중이 "AI 코딩 = RAG"로 알고 있습니다. 절반만 맞고, 절반은 2025년에 뒤집혔습니다.

RAG

Retrieval-Augmented Generation☕

질문이 오면 ① 관련 자료를 검색해서 ② 컨텍스트에 붙이고 ③ 모델이 그걸 근거로 답하게 하는 방식. 부품: 임베딩(글→숫자 벡터), 벡터 DB(비슷한 벡터 찾기), 청킹(문서 자르기), 리랭킹(후보 재정렬).

☕ 쉽게 말하면 — 오픈북 시험입니다. 모델의 머리(가중치)를 바꾸는 게 아니라, 시험장에 책을 갖고 들어가게 해주는 것. 환각(1장)의 1차 백신.

대전환: 벡터 → 에이전틱 검색

agentic search☕

2025년 5월, Claude Code는 벡터 검색을 걷어내고 grep(정확한 문자열 검색)으로 갈아탔고 결과는 "압도적으로 더 좋았다". 이후 Cursor·Cline 등이 유사한 방향으로 이동. 에이전트가 검색 도구를 스스로 반복 사용하며 능동 탐색하는 방식이 에이전틱 검색입니다.

❌ 흔한 오해 — "그럼 RAG는 죽었네?"
✅ 사실 — 코드 검색에서 퇴조했을 뿐, 문서·가이드·사내 지식은 여전히 검색형(RAG·지식화)이 정답입니다. 논문 "Is Grep All You Need?"(arXiv 2605.15184)도 노이즈가 커지면 교차점이 생긴다고 답합니다. 요지는 "retrieval is really retrieval-plus-orchestration" — 검색은 하네스와 한 몸.

에이전틱 RAG = 언제, 무엇을, 다시 검색할지 에이전트가 동적으로 결정하고 중간 결과에 따라 전략을 바꾸는 진화형. GraphRAG = 문서를 지식 그래프로 엮어 관계 질문("A와 B의 연결고리는?")에 강해진 변형.

메모리와 LLM 위키 — 잊지 않는 에이전트

에이전트는 세션이 끝나면 전부 잊습니다. 이 망각과 싸우는 4가지 무기.

지식 · 메모리 · 스킬 · 규칙

Skill반복 가능한 작업 절차영구·이식 가능SKILL.md

☕ 쉽게 말하면 — 지식은 책상 위 자료, 메모리는 수첩, 스킬은 몸에 밴 레시피, 규칙은 사규. 넣는 서랍이 다르면 꺼내는 방법도 다릅니다.

컨텍스트 부패 · 압축

context rot · compaction☕

Context rot = 무관한 도구 출력과 낡은 중간상태가 쌓이며 모델이 조용히 정확도를 잃는 현상. 무서운 점: 에러가 안 납니다. Compaction = 창이 차기 전에 대화를 요약해 새 창으로 이어붙이기 — 단, 무손실이 아니라서 압축 직후 "아까 정한 규칙"을 잊는 일이 흔합니다.

실무 결론 한 줄"중요한 결정은 대화가 아니라 파일(저장소)에 적어라." — OpenAI가 "repo가 단일 진실 원천"이라 말한 이유이자, 다음 용어(LLM 위키)의 존재 이유.

LLM 위키

LLM wiki — 세션을 넘는 복리 지식☕

에이전트가 작업하며 알게 된 사실·결정·구조를 마크다운 위키 페이지로 축적하고, 다음 세션이 그걸 읽고 시작하게 하는 지식베이스. Karpathy가 제안한 모델로, "모든 세션이 첫날"인 에이전트에게 어제가 생기게 합니다.

학계 쪽 흐름: A-MEM(스스로 메모리를 연결·진화시키는 에이전틱 메모리), Letta(구 MemGPT)의 3계층(core=RAM / archival=디스크 / recall=대화이력). 다만 코딩 실무의 정직한 결론은 여전히 — 파일/저장소가 최고의 메모리입니다.

부록 — 한 줄 사전

청중이 던지는 단어를 즉시 받아치기 위한 압축 사전. 굵은 글씨는 실제로 나올 확률이 높은 것.

에이전트 기본

Agent — 모델이 도구·순서·분기·중단을 동적으로 결정하며 목표를 향해 반복 실행하는 시스템

Agentic loop — 계획→도구→관찰→판단의 반복

Tool calling — 모델이 "이 도구를 이 인자로"라는 구조화 출력을 내는 것. 실행은 하네스가 함

ReAct — Reasoning+Acting을 번갈아 하는 고전 패턴

Harness — 모델을 제외한 전부(도구·상태·메모리·권한·검증·관측)

Scaffolding — 모델 주위의 코드. 지침·훅·서브에이전트 등 "모델이 보는 세계"를 정의하는 층

Orchestrator — 과업을 분해해 하위 에이전트에 위임하고 결과를 통합하는 상위 에이전트

Subagent — 독립 컨텍스트와 도구 집합을 가진 하위 에이전트

Agent Teams — 팀원 에이전트끼리 직접 통신·작업목록 공유·자율 조율하는 최신 형태

Handoff — 제어권 자체를 다른 에이전트에 넘기는 방식

HITL — 사람 승인 지점을 루프에 넣는 것(Human-in-the-loop)

Task horizon — 에이전트가 자율로 감당하는 과업의 시간 길이

Background agent — 비동기로 돌다가 완료 시 알림/PR로 회수

Cloud agent — 원격 격리 샌드박스에서 저장소를 클론해 작업

컨텍스트·검색

Context window — 한 번에 모델이 볼 수 있는 토큰 한도

Effective context — 실제로 정확도가 유지되는 구간. 광고값보다 훨씬 작다

Context engineering — 창에 무엇을 넣을지 설계하는 규율

Context rot — 무관한 내용이 쌓여 조용히 정확도가 떨어지는 현상

Compaction — 대화를 요약해 새 창으로 이어붙이기

Progressive disclosure — 이름·설명만 먼저, 본문은 필요할 때 로드

Prompt caching — 반복되는 앞부분을 캐시해 최대 90% 절감

RAG — 검색해서 컨텍스트에 붙이는 전처리형 방식

Agentic search — 에이전트가 grep·읽기·목록을 도구로 써서 능동 탐색

Embedding/Vector DB/Chunking/Reranking — 전통 RAG 부품들. 코드 검색에서는 퇴조 중

GraphRAG — 지식 그래프 기반 RAG. 관계 질문에 강함

AGENTS.md / CLAUDE.md — 에이전트에게 주는 프로젝트 지침 파일

SKILL.md — Agent Skills 표준의 스킬 정의 파일

Memory(core/archival/recall) — Letta식 3계층 메모리

LLM wiki — 세션을 넘어 md 페이지로 복리 축적하는 지식베이스

모델

LLM/SLM — 대형/소형 언어모델

MoE — 토큰마다 일부 전문가만 활성화. 큰 총파라미터, 작은 활성 파라미터

Open-weight vs Open-source — 가중치 공개 ≠ 학습데이터·코드 공개. 온프렘 가능 여부는 open-weight로 결정

Quantization — 정밀도를 낮춰 메모리·속도 확보(FP8/INT4/GGUF…)

Distillation — 큰 모델의 행동을 작은 모델에 옮김

Fine-tuning/LoRA — 부분 가중치 조정. 지식화와 혼동 금지

RLVR — 검증 가능한 보상으로 강화학습. 코드·수학 성능의 주 동력

Reasoning model — 답하기 전 생각 토큰을 태우는 모델

Test-time compute — 추론 시점에 계산을 더 써서 성능을 올림

Structured output — JSON 스키마 등으로 출력 형식을 강제

Hallucination/Grounding — 근거 없는 생성 / 근거에 묶기

Knowledge cutoff — 학습 데이터의 시점 한계

규격·실행 환경

MCP — 에이전트↔도구/데이터 연결 규격. host/client/server

Agent Skills — 스킬 개방 표준(agentskills.io)

git worktree — 같은 저장소의 별도 작업 디렉터리. 병렬 에이전트 충돌 방지

Sandbox — 격리 실행 환경(Seatbelt, gVisor, Firecracker…)

Permission modes — allow/ask/deny, plan(읽기전용), bypass(격리 CI 전용)

Hooks — 도구 호출 전후에 스크립트를 끼워 자동 승인·차단

ADE — Agent Development Environment. 에이전트 관제 환경

devcontainer — 재현 가능한 개발 컨테이너

품질·평가

Regression suite — 회귀 방지 테스트 묶음
